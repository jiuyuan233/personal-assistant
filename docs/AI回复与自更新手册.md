# AI 回复与自更新手册

> 这份文档回答用户 2026-11-14 提的两个要求：
> 「**你一定要教会 action 里的 AI 如何回复我消息，以后给我发消息的不是你**」
> 「**教会如何让 action 里的 AI 更新这个仓库**，就按照 md 文档写的要求设置 AI 就好，写的尽可能详细，要保证人也能看懂」
>
> 两类读者都照顾：**接手的 AI** 按章节照做即可；**用户本人**看 §1、§2、§4、§6 就知道自己的助手每天在干什么、哪些事它做不到、要它做到需要你补什么。
>
> 配套文档：[AI 运维手册](AI运维手册.md)（怎么改代码、怎么验证、怎么派发） · [AI 提示词](AI提示词.md)（每套提示词的全文与调参） · [AGENT.md](../AGENT.md)（六条铁律） · [不足与风险](不足与风险.md)（已知缺陷与平台限制）

## 0. 先把一件事说清楚：Actions 里的「AI」不是一个常驻的人

很多人以为「GitHub Actions 里的 AI」是一个一直在线、能收发消息、能自己改代码的机器人。**它不是。**

真实情况是：

- 每 20 分钟，GitHub 起一个**全新的临时容器**（美国 Azure 机器），检出仓库、装依赖、跑 `python scripts/main.py tick`，跑完容器就销毁。
- 容器里的 Python 在需要时**调一次 AI 接口**（`scripts/ai_client.py` → ChatAnyWhere 中转站 → `deepseek-v3.2`），拿到一段文本或一份 JSON，然后继续跑自己的确定性逻辑。
- AI **没有记忆**：这一轮不知道上一轮说过什么。它的「记忆」就是仓库里的 `data/*.json` 和提示词。
- AI **不能主动找你说话**：只有代码调用它、并且代码决定发送时，你才会收到消息。
- AI **收不到你的回复**：飞书自定义机器人 webhook 是**单向**的（详见 §4）。

所以本仓库里「AI 回复你」的准确含义是：

> **到点时，程序把你的真实数据整理成事实清单，交给 AI 写一段符合人设的中文人话，再由程序把清单、一言、图片确定性地拼在后面，通过飞书发给你。**

「AI 更新仓库」的准确含义是：

> **采集到的数据由 workflow 自动 commit & push（全自动，每 20 分钟）；代码与文档的修改由人发起的一次 AI 会话完成（半自动，必须过门禁）。**

这不是偷懒，是这套架构的能力边界。边界内的事已经做到「一条不漏、失败也发」；边界外的事 §4.3 和 §5.3 给了可落地的升级路线，**都需要用户点头才做**（涉及新凭据、新权限或新的自动化风险）。

## 1. 一条飞书消息是怎么生出来的（完整链路）

以早报为例，九步。每一步都标了「谁做 / 联不联网 / 失败会怎样」——这是排查问题的地图。

| # | 做什么 | 代码位置 | 联网 | 失败会怎样 |
|---|--------|----------|------|-----------|
| 1 | 判断今天这个时段发没发过、现在是否在补发窗口内 | `main.due_pushes()` + `data/runtime.json` 的 `pushed` | 否 | 不发（正常，每天每时段只发一次） |
| 2 | 把日记/作业/公告整理成**确定性事实清单** | `daily_push.diary_facts()` / `study_facts()` / `notice_facts()` | 否 | 数据为空就如实说「没有」，不编造 |
| 3 | 取一条一言 | `daily_push.hitokoto()` → `https://v1.hitokoto.cn/` | 是 | 返回空串，消息照发，只是没有一言 |
| 4 | 取一张二次元图（**只有早报**） | `anime_image.run()` → nekos.best | 是 | 返回 None，消息照发，只是没有图 |
| 5 | 让 AI 写**人话部分**（问好/调侃/鼓励/总结） | `AIClient.chat_text(prompts.push_messages(...))` | 是 | 抛异常 → 走第 6 步的降级文案 |
| 6 | AI 挂了就用人设固定的降级开头 + 事实清单 | `daily_push.fallback_message()` | 否 | 不会失败（纯字符串拼接） |
| 7 | 把**清单**拼在人话后面（作业/公告/一言） | `daily_push.info_block()` | 否 | 不会失败 |
| 8 | 落盘 `/tmp/push-message.txt` 与 `/tmp/push-image.json` | `daily_push.run()` / `anime_image.run()` | 否 | 写不进去 → workflow 走状态卡片分支，失败报红 |
| 9 | 发飞书：有图发卡片，无图发纯文本；卡片被拒收自动退回纯文本 | `scripts/notify_feishu.js` | 是 | 两条路都失败才真的丢消息，日志里有 `❌` |

发完之后，`main.do_tick()` 把 `runtime.pushed[kind] = 今天`，保证同一天不重复发。

### 1.1 本轮最重要的设计决定：人话与清单分离

**AI 只写人话，清单由程序拼。** 原因很实在：

- 把整条消息交给 AI 复述事实时，它会**漏条目、改日期、把链接抄错**。用户要的是「作业和公告一条不漏」。
- 清单不经过 AI，就**不可能被 AI 弄丢**；AI 全挂时清单照样在。
- 提示词里因此明确写着「不要复述清单条目、不要抄日期和链接、不要自己加『今日一言』段落」（`prompts.PUSH_RULES`）。**改提示词时千万别把这几条删掉**，否则消息会翻倍且互相矛盾。

一句话记住分工：**AI 负责「像个人」，程序负责「不出错」。**

### 1.2 作业口径与 README 完全一致

早报的作业清单调用的是 `render_readme.actionable()` + `dedup.sort_by_deadline()`——和 README 任务清单**同一套函数**。所以不会出现「飞书说能做、README 说已逾期」。自检里有一条断言专门锁这件事（`早报作业与 README 任务清单同一口径`）。

## 2. 你会收到哪几种消息

| 消息 | 北京时间 | 内容 | 补发窗口 |
|------|---------|------|---------|
| 🌅 早报 | 07:00 | 中文问好（AI 人话）+ **待完成作业**（≤6 条，每条带可点链接）+ **值得关注的公告**（相关度≥3，≤3 条，带链接）+ **今日一言** + **二次元图**（P 站图源优先） | 5 小时（到 12:00） |
| ☀️ 午安 | 12:00 | 问好 + 鼓励（AI 人话）+ 下午最该动的一件事 + 今日一言 | 5 小时（到 17:00） |
| 🌙 晚安 | 22:00 | **对当天日记的总结**（AI 人话）+ 今天到期还没做完的作业数 + 今日一言 | 2 小时（到 24:00，不跨零点） |
| ⏰/❌ 状态卡 | 不定时 | **只在重要时发**：运行失败/取消，或日志出现 `[urgent]`（24 小时内截止、且这批任务与上轮不同） | — |

三条硬规矩：

1. **永远不带课表。** 用户明确说「不用给我发要上什么课」。自检断言 `三个时段的清单都不带课表` 锁住这点。
2. **常规成功不汇报。** 用户 2026-11-14：「正常运行的不用给我汇报，飞书现在书的信息太多了」。降噪闸门在 `notify_feishu.js`：`status === 'success' && urgent.length === 0` → 打印一行日志后 `process.exit(0)`，**不发任何消息**。
3. **内容可以多于点名的，但不能少于点名的。** 所以早报除了作业/公告/一言/图，还带了日记里的计划统计（降级路径）；晚安除了总结还带了当天到期未完成数。

### 2.1 `[urgent]` 为什么只认「24 小时内截止」且要去重

这是本轮修掉的一个真实噪音源，接手 AI 必须理解，否则很容易改回去：

- **逾期任务不算紧急**：它已经做不了了，README 把它剔到[已剔除任务](已剔除任务.md)，而且逾期数是**常驻**的（实测长期 2 条）。拿它当「重要」→ 每小时一轮的 study 永远发卡 → 正是用户抱怨的噪音。
- **同一批任务不重复告警**：`study_collector.urgent_alerts(soon, prev_sig)` 算出签名存进 `data/study/meta.json` 的 `urgent_sig`，下一轮比对；相同就只打 `[urgent-same]`（JS 不认这个前缀，所以不发卡）。
- **签名只用任务 ID，不含截止时间**：`deadline_exact=False` 的截止时间是「抓取时刻 + 列表页倒计时」**每轮重算**的，带进签名会让它每小时都变，去重直接失效。自检里有一条 `倒计时漂移不会让签名变化` 专门守这个坑。

## 3. 怎么改它说的话（最常见的六类改动）

**改完一律要走 §3.7 的验证流程，不许只改不验。**

### 3.1 改人格 / 说话风格

只有一处：`scripts/prompts.py` 的 `PERSONA`。公告评分、日记挖掘、推送文案全都引用它，改一次全生效。
当前人设是用户指定的「傲娇雌小鬼」：损的是拖延和借口，不是用户这个人；收尾必须落到一句实在的话。

### 3.2 改某个时段说什么

`prompts.PUSH_KIND_BRIEF` 是个字典，三个键 `morning / noon / night`，值就是给 AI 的时段任务说明。
例如想让晚安多夸一句，就改 `night` 那条；**不要**在里面写「把作业清单抄一遍」——那违反 §1.1 的分工。

### 3.3 改长度 / 禁忌

`prompts.PUSH_RULES`。当前：早上和中午 100 字以内，晚上 160 字以内；只准用事实里给出的信息；不许描述图片内容（**AI 看不到图，描述就是编造**）。

### 3.4 改清单内容与条数

`scripts/daily_push.py` 顶部三个常量：

```python
MORNING_TASK_LIMIT = 6      # 早报最多列几条作业
MORNING_NOTICE_LIMIT = 3    # 早报最多列几条公告
NOTICE_MIN_SCORE = 3        # 公告相关度门槛（与 README 公告节一致）
```

要改「列哪些字段」就改 `study_facts()` / `notice_facts()`；要改「哪个时段带哪块」就改 `info_block()`。
**改条数/门槛时记得同步 [AI 提示词](AI提示词.md) 与本文 §2 的表格**，否则文档立刻变成假的。

### 3.5 改 AI 挑名言的标准

用户要求「名言就显示 3 条就可以了，让 workflows 这里的 AI 挑选出有价值的放上去」。实现是两段：

- **打分（联网）**：`prompts.QUOTE_VALUE_INSTRUCTIONS` 定义 0–10 分的评分标准（9–10 = 能当行动准则 … 0–2 = 没信息量），`diary_collector.score_quotes()` 调 AI 给每条名言打 `value` 与 `value_why`，存进 `data/diary/quotes.json`。`diary` 模式每轮顺带补分，`backfill` 模式一次性补全老数据。
- **挑选（零网络）**：`render_readme.pick_quotes()` 按 `value` 降序取前 `QUOTE_LIMIT = 3`，同分按摘录日期新→旧，缺分按 0 排最后。**finalize 不联网、不花 token**（铁律 5）。

想换标准就改评分提示词，然后派发一次 `backfill` 重新打分（注意：`score_quotes` 只给 `value` 缺失的条目打分，**要重打全部得先把 quotes.json 里的 value 字段清掉**，这是有意设计，避免每轮重复烧 token）。

### 3.6 换图片源 / 改图片行为

`scripts/anime_image.py`。选型是**实测**出来的，三条路的结论写在文件文档串里，别凭感觉换：

- 直接爬 P 站：`www.pixiv.net` / `i.pximg.net` 国内出口实测不可达，且要登录态。
- lolicon setu v2：**弃用**。`r18=0` 并不安全，实测返回里出现带 `R-18` 标签却 `r18:false` 的条目，以及 `小学生`+`全裸` 等标签；黑名单通过率只有 25% 且仍有漏网。**每天自动发这种图不可接受。**
- nekos.best（采用）：公开 SFW 图库，实测 48 张里 34 张 `source_url` 指向 pixiv.net，带画师名与作品页链接，可溯源；图床国内可直连。取 5 张候选优先挑 Pixiv 图源，命中率≈99.8%。

换源必须重新做安全实测，并把证据写进文件文档串与[不足与风险](不足与风险.md)。

### 3.7 每次改完必须做的验证（可复制）

```bash
# ① 本地门禁：静态检查 + 离线自检（与 runner 完全一致的两条）
ruff check scripts --select E9,F63,F7,F82,F821,F401
python scripts/main.py selftest          # 期望：失败 0 项

# ② 渲染一遍，确认 README 没被改坏（零网络零 token）
python scripts/main.py finalize

# ③ 推上去，派发对应模式（串行！并发组只保留一个 pending）
#    改推送文案 → 派发 morning / noon / night
#    改名言打分 → 派发 backfill，再派发 finalize
#    改采集器   → 派发 study / diary / notice
#    只改文档   → 派发 selftest 即可

# ④ 读日志验收（关键字见 AI运维手册 §5 与 §8）
#    推送：[push] morning 文案 N 字，一言有/无，图有/无，文案来源：AI/降级
#    图片：[image] 选中 neko · 画师 … · 图源 P站
#    打分：名言价值打分：补上 N 条
#    降噪：[feishu] 常规成功且无紧急任务，按用户要求静默（不发卡）
```

**没有读到日志里的成功证据，就不许说「验证通过」。** 这是本仓库的开发习惯之一（见[开发习惯](开发习惯.md)）。

## 4. 它能不能「回」你的消息？

### 4.1 现状：不能，原因是 webhook 单向

飞书**自定义机器人 webhook** 只有一个入口：你往那个 URL POST 一段 JSON，群里就出现一条消息。它**没有任何回调**——你在群里回它、@它、私聊它，它都收不到。所以现在的「回复」本质是**定时播报**，不是对话。

### 4.2 要做到真双向，缺三样东西

1. **飞书企业自建应用**（拿到 `App ID` / `App Secret`，能换 `tenant_access_token`）；
2. **事件订阅**（`im.message.receive_v1`，飞书把用户消息推给你的服务器）；
3. **一个公网可达、常驻的回调地址**（HTTPS，能验签、能 3 秒内响应）。

**GitHub Actions 当不了第 3 样**：它没有常驻进程，也没有公网入口，只在被触发时活几十秒。这是平台性质，改配置改不出来。

### 4.3 三条可落地的升级路线（都未实现，需用户授权）

| 路线 | 怎么做 | 延迟 | 需要用户做什么 | 代价 / 风险 |
|------|--------|------|---------------|------------|
| **A. 真双向** | 自建应用 + 事件订阅 + 云函数/轻量服务器常驻回调，回调里调 AI 再回消息 | 秒级 | 建应用、开权限、买/开一个云函数或服务器 | 多一个常驻服务要维护；凭据多一套；回调必须验签，否则任何人都能伪造消息 |
| **B. 准双向（最贴合现有架构）** | 自建应用 + 机器人进群，Actions 每 20 分钟用 `GET /open-apis/im/v1/messages` 拉群消息，发现新提问就调 AI 回答并发回群里 | ≤20 分钟 | 建应用、开「读取群消息」权限（**属敏感权限，可能要审批**）、把应用机器人拉进同一个群 | 不需要服务器，完全跑在现有 cron 里；但读群消息权限不一定批得下来，且要把「已处理到哪条」记进 `data/runtime.json` |
| **C. 换收件箱（零新增凭据）** | 用 GitHub Issue 当对话入口：你开一个 issue 提问，Actions 定时读 issue → 调 AI → 用 `GITHUB_TOKEN` 发评论回答 | ≤20 分钟 | 什么都不用建，只需在 issue 里说话 | 不在飞书里；workflow 要加 `permissions: issues: write`；公开仓库里对话内容也是公开的（**隐私风险，必须先想清楚**） |

**接手 AI 注意**：这三条都涉及新凭据/新权限/新自动化，**不得自行开工**。先把现状和选项讲给用户，等他选。路线 B 是性价比最高的，因为它不需要任何常驻服务。

### 4.4 现在就能做的「像对话」的事

不改架构也能提升「被回应」的感觉，且都在现有能力内：

- 晚安总结里**点名他昨天写下的计划**做到没有（数据来自日记写回的复选框，`diary_writeback`）。
- 早报里**提一句他日记里的原话**（`quotes.json`，一字未改）。
- 中午那件事**从他的真实待办里挑**，而不是空泛鼓励。

这些都已经实现或只差改提示词，**不需要新凭据**。

## 5. 它怎么更新这个仓库

### 5.1 数据更新：全自动，每 20 分钟

workflow 的「提交数据」步骤（`.github/workflows/assistant.yml`）：

```bash
case "$MODE" in
  tick|finalize|all) git add data docs README.md ;;   # 渲染产物一起提交
  *)                 git add data                     # 采集模式只提交自己采到的数据
                     git checkout -- README.md docs ;;# 派生产物统一交给 finalize，避免两处渲染打架
esac
git commit -m "chore(data): ${MODE} update <UTC 时间>"
git pull --rebase origin "$REF_NAME"
git push origin "$REF_NAME"        # 推不上去就让这步失败，飞书报红，人来处理
```

要点：

- **不 force push**（铁律 3）。历史上两次 force push 都是用户明确授权的一次性隐私清除，**接手 AI 不得自行发起**。
- 采集模式**不提交 README/docs**，否则两个模式各自渲染同一份 README，rebase 必冲突并丢掉采集结果。
- `probe / selftest / studydiag` 不产生数据，三时段推送只读不写，都跳过提交。
- 提交身份是 `github-actions[bot]`，与人工提交区分得开。

### 5.2 生成物禁止手改（铁律 1）

以下文件**只能由脚本生成**，人和 AI 都不许直接编辑：

`README.md` · `docs/公告.md` · `docs/潜在计划.md` · `docs/已剔除任务.md` · `docs/data/*` · `docs/week.svg` · `data/study/*` · `data/notice/*` · `data/diary/*` · `data/schedule/*` · `data/runtime.json` · `data/diary/plans_archive.json`

唯二手改例外：`data/sources.json`（配置）与 `data/diary/plans.json` 的 `state` 字段（人工标记完成）。
**想改措辞就去改 `scripts/*_template.md`**，然后跑 finalize。直接改 README 会在下一轮被覆盖，白干。

### 5.3 代码与文档更新：人发起的 AI 会话

流程就是 [AI 运维手册 §3](AI运维手册.md) 的五步：**定位 → 改代码 → 同步自检 → 本地验证 → 推送 + Actions 验证**。

为什么不让 Actions 里的 AI 自己改代码？四个理由，每条都是真风险：

1. **公开仓库 + 公开日志**：AI 自主改代码时打的任何日志所有人都看得见，隐私守卫一旦被绕过就是永久泄露（git 历史抹除要用户授权，代价极高）。
2. **凭据在同一个进程里**：自主改代码的 AI 有能力把 Secret 写进文件或打印出来。现在的架构里 AI 只拿到「事实清单」，**根本接触不到凭据**。
3. **没有人审**：一次错误的自动提交可能覆盖采集数据、改坏渲染、甚至触发 force push。
4. **门禁会被绕过**：现在的顺序是「门禁不过就不采集」，自主改代码等于让被检查的对象自己决定要不要检查。

### 5.4 如果用户真想让它半自动改仓库（方案与护栏，未实现）

可以做成这样，**但必须用户明确要求才开工**：

- 入口：`workflow_dispatch` 带一个 `patch` 输入（或读某个指定 issue 里的代码块）。
- 白名单：只允许改 `scripts/prompts.py`、`scripts/*_template.md` 这类「措辞层」文件，**不许碰采集器、workflow、AGENT.md**。
- 强制门禁：改完必须跑 `ruff` + `selftest`，不过就中止。
- 出口：**开 PR，不直推 main**；由人点合并。
- 留痕：PR 正文写清改了哪几行、为什么、验证证据。

这样「AI 更新仓库」就成立，且风险被关在笼子里。**当前没有实现，不要假装它有。**

## 6. 图片链路与飞书应用凭证（用户唯一需要动手的一件事）

### 6.1 为什么现在的图是「按钮」而不是「真图」

飞书自定义机器人 webhook **不能用 URL 内嵌图片**。卡片的 `img` 元素只认 `image_key`，而 `image_key` 必须：

1. 用**企业自建应用**的 `App ID` + `App Secret` 换 `tenant_access_token`（`POST /open-apis/auth/v3/tenant_access_token/internal`）；
2. 下载图片，再 `POST /open-apis/im/v1/images`（`image_type=message`）上传，返回 `image_key`。

webhook 本身没有这个能力。所以代码做了**双路径**：

| 条件 | 你收到的样子 | 代码 |
|------|-------------|------|
| 配了 `FS_APP_ID` + `FS_APP_SECRET` | 卡片里**内嵌真图** + 「🔗 图源作品页」按钮 | `anime_image.upload()` 返回 image_key → JS 放 `img` 元素 |
| 没配（**当前状态**） | 卡片里「🖼 点开今天的图」+「🔗 图源作品页」两个按钮 | `upload()` 直接返回空串 → JS 放按钮 |
| 取图失败 | 纯文本消息，没有图 | `fetch()` 返回 None → JS 走 text 分支 |
| 卡片被飞书拒收 | 自动退回纯文本，图以链接形式补进去 | JS `pushFallbackText()` |

**四条路都不会让消息断掉。** 这是用户要求的「宁可文案糙一点，也不能断」。

### 6.2 想要内嵌真图，用户要做的四步

1. 在[飞书开放平台](https://open.feishu.cn/)创建**企业自建应用**（个人也可以建企业，免费）。
2. 给应用开通**上传图片/文件资源**的权限（控制台里是 `im:resource` 一类），并发布一个版本使权限生效。
3. 拿到 `App ID` 与 `App Secret`，填进仓库 Secrets，名字必须是 **`FS_APP_ID`** 和 **`FS_APP_SECRET`**（填法见 [AI 运维手册 §6.8](AI运维手册.md)，用 API 加密上传，不用开网页）。
4. 确认应用与 webhook 机器人**在同一个企业/租户**里，否则换来的 `image_key` 机器人用不了。

**填完不需要改任何代码**：`upload()` 检测到凭证就自动走内嵌路径。

⚠️ **诚实交代**：内嵌路径（`upload()` 的联网部分）**尚未真实验证过**，因为凭证只能由用户创建。离线部分已验证：无凭证时返回空串、不下载、不联网（自检断言 `没配飞书应用凭证时不上传`）；JS 侧两种卡片结构都已用离线拦截验证（有 image_key 出 `img` 元素，无 image_key 出按钮）。凭证到位后**第一件事就是派发一次 morning 并读日志确认 `[image] 已换取 image_key`**。

### 6.3 图片的安全与署名

- 源是 **nekos.best**（公开 SFW 图库），**不是**直接爬 P 站，也不是 lolicon（弃用理由见 §3.6）。
- 优先挑 `source_url` 指向 `pixiv.net` 的候选，所以大多数图**能溯源到 P 站作品页**；卡片里保留画师名与作品页链接，尊重作者署名。
- 不是 Pixiv 图源时**如实标注**为「网络」，不谎称 P 站。
- 图片超过 8MB 或下载到的不是 `image/*` → 退回链接模式，不硬发。

1. 读 [AGENT.md](../AGENT.md) 六条铁律，**一条都不许违反**。
2. 读 [AI 运维手册 §0–§1](AI运维手册.md)，再读本文 §0–§2，建立「AI 只是被调用的一段能力」的正确认知。
3. 读 [不足与风险](不足与风险.md)，分清「真缺陷」「平台限制」「不是缺陷别乱改」。
4. 跑本地门禁：`ruff check scripts --select E9,F63,F7,F82,F821,F401` + `python scripts/main.py selftest`，确认**失败 0 项**。
5. 派发一次 `selftest`，**读日志**确认 runner 上同样 0 失败（本地过不代表 runner 过）。
6. 看 `data/diary/quotes.json` 有没有 `value` 字段；缺就派发 `backfill` 补打分，再派发 `finalize`，确认 README 名言节是 3 条且带「AI 价值 N/10」。
7. 派发一次 `morning`（**会真的给用户发一条飞书**，别反复派发），读日志确认 `[push] morning … 图有 … 文案来源：AI`。
8. 确认降噪生效：随便一轮常规成功的 tick，日志里应有 `[feishu] 常规成功且无紧急任务，按用户要求静默（不发卡）`，且用户**没收到**状态卡。
9. 把本轮改动写进 [CHANGELOG.md](../CHANGELOG.md)，同步所有受影响的 md（**文档与代码不一致就是缺陷**）。
10. 收工前跑 [AI 运维手册 §10](AI运维手册.md) 的自检清单。

**不要做的事**：force push · 修改两个参考仓库（`Lottery-BiliBiliToolB-Web233` / `wool-gathering`）· 手改生成物 · 把凭据或私人目录名写进任何文件（**注释和修复说明也不行**）· 自行发起 git 历史清除 · 没读日志就说「验证通过」· 自行开工 §4.3 / §5.4 的升级路线。

## 8. 术语小词典（给用户看的）

| 词 | 人话解释 |
|----|---------|
| **webhook** | 一个「往这个网址寄信，群里就会显示」的收件地址。只能寄进去，不能回信。 |
| **image_key** | 飞书内部给图片发的「身份证号」。卡片只认证号，不认外部图片网址。 |
| **cron** | 定时器。本仓库只有一条：每 20 分钟响一次。 |
| **tick** | 定时器响一次时跑的模式。它自己决定这轮该采集什么、该发什么推送。 |
| **finalize** | 把数据渲染成 README 和文档。**不联网、不花 AI 额度**，所以可以每轮都跑。 |
| **门禁** | 干活之前的两道检查：静态检查（抓语法/未定义名字）+ 离线自检（208 条断言，含私人路径守卫；不设 `DIARY_EXCLUDE` 时少一条）。不过就不采集。 |
| **降级** | AI 或一言或图挂了的时候，用确定性内容顶上，保证消息照发。 |
| **签名去重** | 把「这批紧急任务的 ID」算成一个指纹存起来，下轮指纹没变就不再打扰你。 |
| **补发窗口** | 定时器可能晚点（实测最长间隔 4 小时 40 分）。错过整点后仍允许补发的时长。 |
| **生成物** | 由脚本自动写出来的文件。手改会在下一轮被覆盖，所以禁止手改。 |
