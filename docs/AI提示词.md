# AI 提示词

提示词全部集中在 `scripts/prompts.py`，改一处即可。客户端在 `scripts/ai_client.py`。
**改完提示词之后，用户实际收到的那条消息长什么样、怎么验证**，见 [AI回复与自更新手册.md](AI回复与自更新手册.md)。

## 用在哪、不用在哪

| 环节 | 用 AI？ | 理由 |
|---|---|---|
| 学习通作业/考试 | ❌ | 纯结构化 HTML，正则足够，且每小时跑一次，用 AI 既贵又不稳定 |
| 课表解析 | ❌ | ICS 是标准格式，确定性解析 |
| 公告相关度 | ✅ | 「这条通知对我有没有用」是语义判断，关键词做不到 |
| 日记名言/潜在计划 | ✅ | 「隐含意图」只能靠理解 |
| 名言点评（`comment`） | ✅ | 用户明确要求「加上 AI 的点评」，走 PERSONA 人格 |
| 名言价值分（`value`） | ✅ | 用户要求「显示 3 条，让 AI 挑选出有价值的」。**打分联网，挑选离线** |
| 日记复选框 | ❌ | 正则 100% 准确，比 AI 可靠，且不受模型抖动影响 |
| 日记写回 | ❌ | 确定性渲染 + pid 对齐，**绝不让 AI 碰用户正文** |
| 早/中/晚飞书文案 | ✅ | 要人格、要鼓励、要总结，模板写不出来 |
| 推送的事实清单 | ❌ | `daily_push.diary_facts()` / `study_facts()` / `notice_facts()` 确定性拼装，再由 `info_block()` 追加到文案末尾。**AI 只写人话（prose），不许编事实、也碰不到清单** |
| README 渲染 | ❌ | **每 20 分钟一次，必须零 token** |

`DETAIL_SCHEMA` / `DETAIL_INSTRUCTIONS`（公告正文摘要）**已接线**：`notice` 模式对
`score >= 4` 且尚无摘要的公告抓正文，每次最多 `DETAIL_MAX = 5` 条，抽 `summary` → `description`、
`deadline` → 报名截止日。正文容器是博达 CMS 的 `v_news_content`（www 与 jwc 两站实测一致）。

**为什么必须抓正文**：只给标题时，提示词里「不要编造」会让模型正确返回 `deadline: null`，
于是 [docs/公告.md](公告.md) 的「截止」列恒为 `—`。截止日几乎都写在正文里，不读正文就拿不到。

**`max_tokens` 不能低于 2000**：首次接线用 1000，结果 3 条全部返回空内容、`0/3` 补全，
且当时三个跳过分支都是静默 `continue`，日志里连 WARN 都没有，极难定位。现已统一 2000
并给每个跳过分支补了告警。

**`deadline` 不能只靠提示词约束（2026-11-13 实测）**：第一版无条件采纳模型返回值，
三个日期里两个是错的 —— 一个把「学院初赛阶段10月1日—10月30日」的结束日当报名截止，
另一个（`2026-09-18`）正文里根本不存在，是凭空编的。
把 `DETAIL_INSTRUCTIONS` 收紧成「只取正文明确写着报名截止/截止提交/逾期不予受理的那个日期，
赛程阶段起止日、发文日期、活动举办日期一律不取」之后清空重抽，
**摘要质量变好了，三个截止日一字未变**。

所以提示词只是第一层，硬约束在代码里：`notice_collector.deadline_supported(text, dl)`
要求正文同时满足①出现报名截止语义（`DEADLINE_CUE_RE`）②该日期能在正文里找到
（兼容 `2026-05-31`／`2026年5月31日`／`5月31日`／`5.31` 等写法），否则丢弃并 WARN。
真实 runner 上已验证拦掉 `2026-10-30`，保留有原话依据的 `2026-05-31`。

改提示词或换模型后，**别只看「补全 N/N」就当成功**，要拿真实公告正文复核日期。
另注意 `ai_detail()` 只在 `deadline` 为空时写值，存量错值不会自动纠正，需手工清
`data/notice/notices.json` 对应字段。详见 `docs/技术路径.md`「截止日为什么不能只靠提示词」。

## 配置

| 环境变量 | 来源 | 默认 |
|---|---|---|
| `AI_API_KEY` | Secret | 无（缺失时抛 `MissingCredential`，**不是 `sys.exit`**，见下） |
| `AI_BASE_URL` | Variable | workflow 里兜底 `https://api.chatanywhere.org/v1` |
| `AI_MODEL` | Variable | workflow 里兜底 `deepseek-v3.2`（**点号**，写成 `deepseek-v3-2` 会每次 403） |

`AIClient` 类内部的默认值（`api.openai.com/v1` + `gpt-4o-mini`）只在**本地不设环境变量**时生效，
Actions 里永远被 workflow 的 env 覆盖。换中转站只改 Variable，不用改代码。

**`AI_API_KEY` 缺失时的行为（审计 §4.5 已修，2026-11-14）**：

- 旧实现用 `env("AI_API_KEY", required=True)`，缺失时 `sys.exit(1)` → 抛 **`SystemExit`**。
  而 `SystemExit` 继承 `BaseException`，**`except Exception` 捕不到** →
  `daily_push` 写好的 `fallback_message()` 降级文案永远用不上，整个推送步骤直接死掉。
- 现在改成 `env("AI_API_KEY")`（不 required）+ 显式 `raise MissingCredential("AI_API_KEY 未配置")`，
  **`MissingCredential` 是 `RuntimeError` 的子类**，普通 `except Exception` 就能接住。
- 两个采集器仍保留 `except SystemExit` 分支作为兜底（别删，其他地方可能还有 `env(required=True)`）。
- **所以没配 AI 也能跑**：公告退回关键词打分、日记只做复选框解析、推送走降级文案。
  只是相关度粗糙、挖不出隐含计划。

## 客户端的三个防线

1. **滑动窗口限流**：`RateLimiter(45 次 / 300 秒)`，接近阈值就 sleep 到安全位置
2. **重试**：3 次，429 退避 `5×attempt` 秒，其他异常 `2×attempt` 秒
3. **三级 JSON 抽取**（`_extract_json`）：裸 JSON → ` ```json ` 代码块 → 首个 `{`/`[` 到末个 `}`/`]`

**不用 function calling**：部分中转站不支持 `tools` 参数，直接报错。
改为在 system 里硬性要求「只输出合法 JSON」+ 传 `schema_hint`，再靠三级抽取兜底。通用性优先。

**`max_tokens` 的坑**：推理型模型（deepseek-r1 / o 系列）会把思考过程算进 `max_tokens`，
给 2000 可能全被思考吃掉、`content` 返回空。当前默认 `deepseek-v3.2`（**点号**）是非推理模型，
2000 够用；实测给 1000 时正文摘要会返回空 `content`，表现为「补全 0/3」且无报错。
**换成推理模型时要把 `max_tokens` 提到 8000+**，否则表现为「AI 返回结构异常」但日志里没有报错。

## 用户画像（USER_PROFILE）

**六套提示词**（公告评分 / 日记挖掘 / 名言点评 / 公告正文摘要 / 三时段推送 / **名言价值打分**）
共用同一段画像，改它就能整体调整取向。当前内容要点：

- HUUC 本科生，建筑环境与能源应用工程
- 从课表专题（`计算思维与人工智能[Agent系统搭建]`、`强化学习-路径规划`、`智能数据分析与报告生成`）
  推断出对 AI / Agent / 数据分析有明确兴趣，且有编程能力
- **关注**：学科竞赛、大创、科研、奖学金评优、技能证书、实习就业、能写进简历的实践
- **不关注**：纯行政、放假调课、面向教师的会议、党建学习、校友联谊

画像写得越具体，评分越准。换专业/换兴趣时**只改这一段**。

## 公告评分（NOTICE_INSTRUCTIONS）

0–5 分，标准在提示词里逐档写死，避免模型自由发挥：

| 分 | 含义 |
|---|---|
| 5 | 必须行动：有明确报名/提交截止日期，且用户可直接参与的竞赛、大创、项目、奖学金 |
| 4 | 强烈建议：与专业或 AI 兴趣高度相关的竞赛、科研、实习、认证 |
| 3 | 值得知道：面向全体学生的有益机会（讲座、培训、志愿者、双选会） |
| 2 | 弱相关：需要特定身份或条件，用户可能不符合 |
| 1 | 基本无关：行政通知、面向教师、党建、后勤 |
| 0 | 完全无关：放假、调课、值班、会议报道、新闻宣传 |

约束：`category` 只能从 8 个固定值里选；`deadline` **不许编造**，判断不出就 null；
`reason` ≤20 字；`index` 必须与输入序号一一对应。

**调用参数**：`temperature=0.1`（打分要稳定）、`max_tokens=2000`、每批 10 条、单次上限 30 条候选。

**成本控制的关键**：只有 `id` 不在旧库里的**新公告**才送 AI。
已评过的公告靠 `merge_notices` 沿用旧分数，所以 notice 模式（**约每 6 小时一次**，
由 `main.TICK_INTERVALS["notice"] = 360` 分钟决定，不是 cron）实际 token 消耗很低。
候选还要先过关键词门（`block` 一票否决、`gate` 命中才入围），进一步砍掉无关项。

**两个阈值别搞混**：README 展示 `score >= 3`，飞书「高相关」计数 `score >= 4`。

## 日记挖掘（DIARY_INSTRUCTIONS）

`temperature=0.2`、`max_tokens=2000`、单文件正文上限 6000 字符（`sources.json` 可调）。

**quotes（名言）** 的判定标准：

- 必须是**用户自己的话**，抄录的名人名言/歌词/书摘一律不要
- 有观点、有情绪、有自我要求（「我要…」「不能再…」「…才是真的…」）
- 不是流水账（「今天上了高数课」不算）
- `text` **逐字摘录，一字不改**，只允许去首尾空白和 Markdown 标记
- 宁缺毋滥：一篇通常 0–2 条，没有就空数组

**plans（潜在计划）** 最重要的一条约束：

> Markdown 复选框 `- [ ]` / `- [x]` 已经由程序确定性解析过了，**不要重复输出复选框里的待办**。

不写这句，模型会把复选框原样抄一遍，导致同一条待办出现两次（`origin` 不同 → ID 不同 → 去重抓不住）。
AI 只负责挖**没写成复选框的意图**：正文明说但没列待办的、隐含的（「一直想学…」「要是能…就好了」）、反复出现的念头。

`confidence` 三档写死：明说 0.9 / 强意向 0.7 / 模糊 0.4。
`state` **一律 "open"**——是否完成由人工或复选框决定，不让模型判断（模型会瞎猜）。
`due_date` 推断不出就 null，不许编造。

**`comment`（名言点评）**：40 字以内，必须针对这句话本身 —— 指出它体现了什么、
哪里在自我欺骗、或下一步具体该做什么。不许空泛夸奖、不许复述原句，没话说给空字符串。
风格走下面的 `PERSONA`。落盘时 `safe_text(..., 120)` 截断。

实测样例（2026-11-13，真实 runner）：

> 句：今天早上起来做的很棒没有刷短视频👏
> 评：哼，一天没刷就邀功？把这股劲儿固定成早起流程，别靠心情。

点评要落到**具体动作**上，这条样例是合格线。

## 名言点评回填（COMMENT_INSTRUCTIONS / comment_messages）

**为什么单独有一套提示词**：日记挖掘里的 `comment` 是**顺带**产出的 —— 只有 sha 变化的文件才重跑 AI，
老日记不再处理，于是**空 comment 永远空着**（审计 §3.3 实测：15 条名言只有 8 条有评论）。
`backfill` 模式专门补这个洞，它需要一套**只点评、不挖掘**的提示词。

| 项 | 值 |
|---|---|
| Schema | `COMMENT_SCHEMA = '{"comments": ["", ""]}'` |
| 输入 | `序号. 「原句」（语境：context）` 逐行 |
| 输出 | `{"comments": [...]}`，**数组长度必须等于输入条数** |
| 人格 | 共用 `PERSONA`（傲娇雌小鬼），与推送同一份 |
| 字数 | 每条 ≤40 字，落盘再 `safe_text(..., 120)` 截断 |

**三条硬约束写在提示词里**：

1. 必须针对这句话本身 —— 指出它体现了什么、哪里在自我欺骗、或下一步具体该做什么。
   **不许空泛夸奖，不许复述原句。**
2. **按输入序号一一对应**，没话说的给**空字符串**，不要跳过。
   跳过会让数组长度对不上，回填时错位到别的名言上。
3. 走 `PERSONA`，但**硬边界同样适用**（不许人格羞辱、不许越界）。

**调用方**：`diary_collector.backfill_comments()`，由 `main.py` 的 `backfill` 模式触发。
**两个出口都连带调 `score_quotes()`**（见下一节），所以跑一次 `backfill` 同时补点评和价值分。
日志关键字（**selftest 锁死了它们，改文案要同步改 [AI运维手册](AI运维手册.md)**）：

- `名言点评回填：补上 N 条，仍空 M 条（共 K 条）`
- 第二次跑（全部已有评论）：`N 条全部已有评论，无需回填`

**幂等**：只补 `comment` 为空的条目，已有评论的不动。所以可以反复跑，不会重复烧 token。
**「全都补过了」也算成功**（`ok = filled > 0 or sv["ok"]`）—— 否则存量补齐之后再跑会假报失败。
**验收别只看「补上 N 条」**，要打开 README 的 `## 📔 我的名言` 区块
（全量数据在 [data/diary/quotes.json](../data/diary/quotes.json)），
确认点评真的落到了对应的那句话上 —— **序号错位是这套提示词最容易出的 bug**，
而「补上 N 条」这个日志对错位是盲的。

## 名言价值打分（QUOTE_VALUE_INSTRUCTIONS / quote_value_messages）

**为什么有这一套**：用户 2026-11-14 原话「名言就显示3条就可以了，让这里的 AI 挑选出有价值的放上去」。
「挑选」拆成两半，**只有打分这一半联网**：

| 阶段 | 谁做 | 联网 / 花 token |
|---|---|---|
| 打分 | `diary_collector.score_quotes(batch=10)` → 写 `quotes.json` 的 `value` / `value_why` | ✅ |
| 挑选 | `render_readme.pick_quotes()` 按 `value` 降序取前 `QUOTE_LIMIT=3` | ❌（铁律 5） |

| 项 | 值 |
|---|---|
| Schema | `QUOTE_VALUE_SCHEMA = '{"values": [{"index": 0, "value": 0, "why": ""}]}'` |
| 输入 | `序号. 「原句」（语境：context）` 逐行 |
| 输出 | `{"values": [...]}`，**数组长度必须等于输入条数** |
| 人格 | **不走 PERSONA** —— 这是打分不是聊天，要稳定可复现，`temperature=0.3` |
| 落盘 | `value` 夹到 0–10 整数；`value_why` 走 `safe_text(..., 40)` |

**打分档位写死在提示词里**（避免模型自由发挥，和公告评分同一思路）：

| 分 | 含义 |
|---|---|
| 9–10 | 能当行动准则：具体、可执行、戳中他正在逃避的事 |
| 7–8 | 有真实自我要求或清醒的自我认知，值得反复提醒 |
| 5–6 | 有情绪有态度，但偏口号，行动指向弱 |
| 3–4 | 接近流水账或空泛感叹 |
| 0–2 | 没有信息量，或与他的目标无关 |

`why` 要求 **12 字以内**、针对这句话本身。**存下来供追溯，README 与看板都不渲染它。**

**触发点有两处**：`diary` 采集末尾当场给新名言打分（不用等 backfill）；
`backfill` 模式补存量。打分失败只 WARN/ERROR，**不抛异常** —— 缺 `value` 的名言按 0 分排最后，
README 不会开天窗。

日志关键字：`名言价值打分：补上 N 条，仍缺 M 条（共 K 条）`、
`名言价值打分：K 条全部已有分数，无需打分`、`名言价值打分失败（第 N 批）`。

**改挑选标准只改 `QUOTE_VALUE_INSTRUCTIONS`**；改显示条数只改 `render_readme.QUOTE_LIMIT`。
改完必须重跑 `backfill` 才会重新打分 —— **已有 `value` 的条目不会被覆盖**（幂等，省 token）。

⚠️ **想让新标准对存量名言生效，目前没有办法**：`score_quotes()` 只挑 `value is None` 的，
而 `data/diary/*` 是生成物、**禁止手改**（AGENT.md 铁律 1），所以不能靠手动清 `value` 字段绕过。
需要重打分时得**先加一个 `rescore` 模式**（把 `value` 置空再调 `score_quotes()`），
不要直接编辑 JSON。这是已知缺口，写在 [不足与风险](不足与风险.md) 里。

## 人格（PERSONA）—— 只有一份，改这里就全改了

`prompts.py` 的 `PERSONA` 常量被**名言点评**和**三时段推送**共用。
用户明确要求的口味：傲娇的雌小鬼。

- 语气词可用「哼」「啧」「就这？」「别误会，我才不是在关心你」
- **结构固定：先损一句，再落到真正有用的信息或鼓励上。损完必须给实事，不许只损不给。**
- 中文口语短句，不堆 emoji，不用书面腔和客服腔

**硬边界（改这段前先确认它们还在）**：不许真的辱骂或贬低人格；不许拿外貌、家庭、智力、
成绩做人格羞辱；不许色情或任何越界内容；不许鼓励自伤或放弃。
**调侃的对象是「拖延这件事」，不是「用户这个人」。**

## 三时段推送（PUSH_RULES / PUSH_KIND_BRIEF / push_messages）

`temperature=0.8`（比抽取高，要有点活人味）、`max_tokens=2000`。
输出**纯消息正文**，不要 JSON、不要代码块、不要「好的」开场。
字数：**早/中 ≤100 字，晚 ≤160 字**（v1.5.0 收紧过，原来是 120/180 —— 因为清单改由程序追加，
人话部分不需要那么长）。

| kind | 目标时刻（北京时间） | 内容约束 |
|---|---|---|
| `morning` | 07:00 | 中文问好 + 一句实在的鼓励，可以提「作业和公告列在下面了」「图也给你带了」，**不复述清单条目/日期/链接**，**绝对不提课表、不提上课时间** |
| `noon` | 12:00 | 先损一句再给一句具体鼓励，**不许编造上午发生了什么**，不复述清单 |
| `night` | 22:00 | 对当天日记做总结：肯定做到的、点出没做的、给明天一个具体动作，不复述清单 |

**时刻不是 cron，是 `main.PUSH_HOURS` 常量**（v1.4.0 起）。全仓库只有一条 `7-59/20` cron，
`do_tick()` 每轮问 `due_pushes()`：当前小时 ≥ 目标小时、且 `runtime.pushed[kind] != 今天` → 发。
**错过后在 `PUSH_CATCHUP_HOURS = {"morning": 5, "noon": 5, "night": 2}` 小时内仍补发**
（morning 补到 noon 时段为止，noon 补到 17:00，night 只补到当天 24:00）。
窗口之所以按时段给而不是全局一个数：实测 GitHub 两次 schedule 触发间隔达 280 分钟，
全局 3 小时会让整个补发窗口落在间隔里、那个时段的推送被静默丢掉。
按**日期**记账而不是按小时，保证一天最多一次，不会因为补发而重复轰炸。

**四条铁律写在提示词里，也在代码里保证**：

1. **只能用「今日事实」里给出的信息**，不许编造任务/日期/成绩/课程/活动。
   事实由 `daily_push.diary_facts()`（读 `data/diary/*`）、`study_facts()`（读 `data/study/tasks.json`）、
   `notice_facts()`（读 `data/notice/notices.json`）确定性拼装，**都不碰课表**。
2. 事实里没有任务就直说没有，不许硬凑，也不许拿课表来填。
3. 给了「一言」就自然提一句，可以吐槽它，但**不许改它的字**，也不要整段抄录。
   一言源是用户指定的 `https://v1.hitokoto.cn/`，取 `hitokoto` + `from`。
4. **只写人话（prose）**。作业清单、公告清单、一言、图片由 `info_block()` 与 JS 追加，
   所以不许复述清单、不许自己加「今日一言」段落。
   **提到图片时只说「给你带了张图」，不许描述画面内容 —— 模型看不到图，描述就是编造。**

**降级不靠 AI**：AI 失败或返回空 → `fallback_message(kind, facts, hit="")` 出确定性文案。
**`hit` 必须传空串** —— 一言已经由 `info_block()` 拼过一次，再传就会在消息里出现两条重复的一言
（v1.5.0 修掉的真实 bug）。判断用显式 `ai_ok` 布尔，**别改回 `text.startswith(...)` 那种脆判断**。
日志「文案来源：AI / 降级」是唯一可信的成功标志。

实测（2026-11-13，run 43382244174）：`morning 文案 134 字，一言有，文案来源：AI`，飞书推送成功。

## 调参建议

| 症状 | 改哪里 |
|---|---|
| 名言太少 / 太多 | `DIARY_INSTRUCTIONS` 里「一篇通常 0-2 条」的数字，或放宽/收紧判定标准 |
| 名言里混进名人名言 | 强化「抄录的不要」，或加一句「如果这句话能在网上搜到原文，就不要」 |
| 计划和复选框重复 | 检查那句加粗约束是否被删掉了 |
| 公告漏掉重要竞赛 | 先查 `sources.json` 的 `keywords.gate` 是否拦住了（AI 根本没看到它），再调评分标准 |
| 公告太多噪声 | 往 `keywords.block` 加词，比改提示词便宜得多 |
| 评分每天抖 | `temperature` 已经是 0.1；抖动主要由 `merge_notices` 的「score 只升不降」吸收 |
| 换了推理模型后 AI 全空 | 提 `max_tokens` 到 8000+ |
| 想整体换取向 | 只改 `USER_PROFILE` |
| README 名言挑得不对 | 改 `QUOTE_VALUE_INSTRUCTIONS` 的档位描述；**存量不会自动重打分**（见上文缺口） |
| 名言显示条数 | `render_readme.QUOTE_LIMIT`（当前 3），不是提示词 |
| 早报作业/公告条数 | `daily_push.MORNING_TASK_LIMIT` / `MORNING_NOTICE_LIMIT` / `NOTICE_MIN_SCORE` |
| 飞书太吵 | 先确认降噪闸门还在（`notify_feishu.js` 的 `status === 'success' && urgent.length === 0`），再收窄 `urgent_alerts()` 的窗口 |
| 图片风格不喜欢 | `anime_image.py` 的 endpoint（`neko` / `kitsune` / `waifu`），**不要换回 lolicon**（已实测否决） |
