# AI 日常维护手册（给「管日常更新」的 AI）

> **这份文档是写给谁的**：用户会把你（一个对话式 AI）召唤过来，让你照着这份手册
> 维护他的个人助手仓库。**你不负责开发新功能**——那是另一位「开发 AI」的工作
> （它读 [AGENT.md](../AGENT.md)，那是开发者级别的文档，有 500 行，你现在不用读）。
> 你只做本手册里写清楚的小改动，**一条一条照着做就能干对**。
>
> **人类也能看懂这份文档**：每一步都写明了「改哪里、怎么验、改坏了会怎样」。
> 不懂就停下来问用户，**猜着改是这个仓库最忌讳的事**。

## 0. 三分钟上岗（必读，不读不许动手）

### 0.1 你接手的是一个什么仓库

`jiuyuan233/personal-assistant`——一个**跑在 GitHub Actions 上的全自动个人助手**：

- 每 20 分钟自动巡检一次（学习通作业 / Gitee 日记 / 校园公告 / 课表）；
- 把「按截止时间排序的任务清单」渲染到 README 和网页看板；
- 每天早 7 / 午 12 / 晚 18 / 夜 22 点用飞书给他发四条消息，外加三种独立提醒
  （6 小时紧急截止 / 新作业发布 / 运行失败报警）；
- 凌晨 0–6 点会把「潜在任务复选框」和「一段 AI 记忆」写进他的 Obsidian 日记。

**你改的每一行文字，第二天会真实出现在他的飞书和日记里**，所以改错了他真的会发现。

### 0.2 六条铁律（浓缩版，全文在 AGENT.md）

1. **生成物禁止手改**。`README.md`、`docs/公告.md`、`docs/潜在计划.md`、
   `docs/已剔除任务.md`、`docs/data/*`、`docs/week.svg`、`data/study/*`、
   `data/notice/*`、`data/diary/*`（含 `memory.json`）、`data/schedule/*`、
   `data/runtime.json`——这些全是脚本自动写的，你手改会被下一轮覆盖，白干还添乱。
   **想改显示效果，改模板**（`scripts/readme_template.md` 等）或提示词，别改产物。
   唯二例外：`data/sources.json`（配置，随便改）和 `data/diary/plans.json` 的
   `state` 字段（人工标完成用）。
2. **凭据一个字都不许出现**在你写的任何文件、注释、提交信息、日志里。
   仓库是公开的，Secrets 里的值（`AI_API_KEY` / `GITEE_TOKEN` / `CX_PASSWORD` /
   `FS_*` / webhook 地址）提到时只写名字，**永远不写值**。
3. **不许 force push**。推不上去就让步骤失败、飞书报红、人来处理。
4. **别动 workflow 结构**（`.github/workflows/*.yml` 的调度、并发组、防失控闸门）
   ——那里每一个看起来奇怪的写法都是修过的真事故，看着多余也别删。
5. **改完必须验证**（§2 三件套），**没看到「失败 0 项」不许说完成**。
6. **拿不准就不做**。本手册没写的任务，一律停手，让用户去召唤开发 AI。

## 1. 你能做的 13 件事（每件四步：改哪里 → 改什么 → 怎么验 → 派发什么）

**开工前先把仓库 clone 下来；每次改完都走 §2 的三件套，过了才提交推送。**

### 1.1 改说话风格（人格）

- **改哪里**：`scripts/prompts.py` 顶部的 `PERSONA`（一段中文描述，写什么风格它就是什么风格）。
- **注意**：改这一处，飞书四时段文案、日记名言点评、每日记忆段落的口吻**全变**。
  硬边界写在 PERSONA 里（不许辱骂人格、不许色情、不许鼓励自伤）——**删掉边界
  属于越权，不许做**。
- **验证**：§2 三件套过 → 提交 → 派发 `morning` 模式 → 日志搜 `[push] morning`，
  确认「文案来源：AI」，然后看用户飞书收到的实际口吻。
- **改记忆的口吻另有一处**：`prompts.py` 的 `MEMORY_INSTRUCTIONS`（每天写进日记的
  那段「助手记得」，和人格共用 PERSONA 但有独立要求，比如长度 ≤120 字、不编造）。

### 1.2 改某个时段的消息内容

- **改哪里**：`scripts/prompts.py` 的 `PUSH_KIND_BRIEF` 字典——`morning / noon /
  dusk / night` 四个键，值是「给 AI 的时段任务说明」。想让晚安多夸一句，改 `night` 那条。
- **不许做**：在里面写「把作业清单抄一遍」——清单由程序拼（设计如此，AI 抄必错），
  写了会导致消息翻倍互相矛盾。

### 1.3 改文案长度上限

- **改哪里**：`scripts/prompts.py` 的 `PUSH_RULES`。当前：早/中午 100 字内，
  晚 160 字内。

### 1.4 改消息里列几条作业/公告

- **改哪里**：`scripts/daily_push.py` 顶部常量：
  `MORNING_NOTICE_LIMIT`（早报公告条数，现 3）、`NOTICE_MIN_SCORE`（公告相关度门槛，
  现 3）。**作业清单没有条数上限**（v2.10，用户 2026-11-28：「通知就通知全部
  可以做的作业，每个通知都是」）——四个时段都带全量清单，不要加回截断。
- **同步义务**：改了条数要同步 [AI提示词.md](AI提示词.md) 和
  [AI回复与自更新手册.md](AI回复与自更新手册.md) §2 的表格——**文档和代码不一致
  在这个仓库里就算缺陷**（有自检断言盯着部分一致性）。

### 1.5 加 / 停一个公告源

- **改哪里**：`data/sources.json` 的 `notice` 数组——复制一条现成的，改 `name` 和
  `url`；`enabled: false` 就是停用。`pages` 是抓几页，`weight` 是相关度权重参考。
- **注意**：新增的站点 HTML 结构未必和现有的一致（日期位置可能不同），
  如果跑完发现新源「新增公告 0」而站点明明有更新，**停手**——适配新结构是开发 AI 的活。
- **验证**：派发 `notice` 模式，日志搜 `抓取站点` 和 `公告合并：新增 N`。

### 1.6 改采集频率

- **改哪里**：`scripts/main.py` 顶部的 `TICK_INTERVALS`——`study: 60`（分钟）、
  `diary: 120`、`notice: 360`。
- **红线**：**别把 study 调到 60 分钟以下**——上一任开发 AI 实测过，连续快速访问
  14 门课会触发学习通**会话级反爬封锁**（几小时解不开，还会危及正常采集）。
  这是硬约束，写在多处文档里。

### 1.7 改推送时刻

- **改哪里**：`scripts/main.py` 顶部的 `PUSH_HOURS`（morning 7 / noon 12 / dusk 18 /
  night 22，北京时间整点）和 `PUSH_CATCHUP_HOURS`（错过整点后的补发窗口小时数）。
- **同步义务**：**同时要改 cron-job.org 上的外部准点 job**（见 §3.2），否则外部
  触发时刻和新窗口对不上。
- **注意**：这是少数要碰「两个系统」的活——拿不准就只改 `PUSH_HOURS` 并把
  cron-job 的事告诉用户，让他决定。

### 1.8 开 / 关某个功能

全在 `data/sources.json`，一行一个：

| 想关什么 | 改哪里 | 备注 |
|---|---|---|
| 随堂作业采集 | `study.quiz_browser` → `false` | 关了随堂任务不再入库 |
| 助手记忆 | `diary.memory_enabled` → `false` | 关了日记里不再有「助手记得」段 |
| 公告正文摘要 | `notice.fetch_detail` → `false` | |
| 随堂每轮抓几门课 | `study.quiz_per_round`（现 4） | 14 门轮一圈约 3.5 小时；**调大要想想反爬** |

### 1.9 把一条计划标成已完成

- **改哪里**：`data/diary/plans.json` 里对应条目的 `"state": "open"` 改 `"done"`。
- **注意**：只许改 `state` 字段，别的字段都是生成的。其实更自然的方式是在日记
  复选框里勾上 `[x]`，系统自己会同步——告诉用户这个更省事。

### 1.10 让某个时段今天重发一次

- **场景**：消息发歪了想让今天再发一遍。
- **改哪里**：`data/runtime.json` 的 `pushed` 里把对应时段的日期改成昨天
  （比如 `"noon": "2026-11-16"` → `"2026-11-15"`），下一轮 tick 就会补发。
- **注意**：这是 runtime.json 唯一允许的手改（其他键动都算破坏）；
  **`runtime.json` 整个删掉 = 全部采集器立即到期 + 今天所有推送重来**，那是重置手段不是日常操作。

### 1.11 处理「消息太吵 / 太安静」

- 太吵：先看是不是状态卡在报错（那是真出错了，修错不是降噪）；确认没错再考虑
  收紧 `NOTICE_MIN_SCORE` 或减条数（§1.4）。
- 太安静（怀疑漏发）：查 `data/runtime.json` 的 `pushed`——今天该发的时段有日期
  就是发过了；没日期就去 Actions 日志里搜 `[push]`。**先查证再改代码**，
  绝大多数「没收到」是飞书群免打扰或 Actions 延迟（补发窗口最长 5 小时）。

### 1.12 换图片源 / 关图片

- **改哪里**：`scripts/anime_image.py`。
- **红线**：换图源**必须重新做安全实测**并把证据写进文件头注释——现在的
  nekos.best 是三选一实测出来的（另一条候选 lolicon 实测会漏 R-18 内容，**弃用**）。
  没条件实测就别换，告诉用户原因。

### 1.13 更新竞赛日历的手工内容

- **改哪里**：`docs/竞赛日历.md`——它是**手工维护文档**（Actions 不碰它），
  加新赛事 / 更新截止日随便改。
- **规矩**：不编日期。查不到的写「待核实」，来源链接贴在对应行。

## 3. 两个外部系统（需要用户账号的操作，你只动嘴不动手）

### 3.1 GitHub Secrets / Variables（你永远不该碰）

`AI_API_KEY`、`GITEE_TOKEN`、`CX_USERNAME`/`CX_PASSWORD`、`FS_APP_ID`/`FS_APP_SECRET`、
`FS_WEBHOOK`、`DIARY_EXCLUDE` 都在仓库 Settings → Secrets and variables 里。
**轮换它们是用户本人的事**；你连值都看不到，也不该尝试看。

### 3.2 cron-job.org（外部准点触发器，用户已建好 4 条 job）

`pa-morning 07:05 / pa-noon 12:05 / pa-dusk 18:05 / pa-night 22:05`（Asia/Shanghai），
每条 job POST 一次 `tick` 给 GitHub Actions，保证四时段推送准点。
**防重复不靠它**——GitHub 侧的接力链和错峰 cron 同时也在跑，三路靠
`runtime.pushed` 按日期记账，谁先发谁算，后到的自动跳过。

- **API 的坑（若用户让你重建 job，原样照做别发挥）**：
  创建用 `PUT /jobs` 且必须包一层 `{"job": {...}}`；`requestMethod` 是**顶层整数**
  （POST=1）；headers 是**对象**不是数组；限流 1 次/秒、5 次/分钟（连发必 429，
  批量操作隔 15 秒）；**months/mdays/wdays 必须给显式数字数组
  （`[1..12]`/`[1..31]`/`[0..6]）**——给 `["*"]` 会被存成 months=[1] mdays=[1]，
  四条 job 全部静默等到 2027 年才触发（2026-11-16 实测踩过）。**建完/改完必须
  GET 复核 `nextExecution` 是当天或次日的准点**，HTTP 200 不代表存对了。
- API key 与它请求头里的 GitHub Token **只在 cron-job.org 服务端和用户的记录里**，
  不许写进仓库任何文件。
- 想临时验证某条 job：把它的 minutes 改到 2 分钟后，等触发，**验完改回原值**
  （上一任这么验过 dusk 档，验完忘了改回的时刻表就是一次事故源）。

## 5. 什么时候必须上交（找开发 AI）

出现下列任何一条，**停手，原样记录，让用户召唤开发 AI**（它读 AGENT.md 上手）：

1. 本手册没有对应操作的任务（加新功能 / 新数据源 / 新消息类型）。
2. 三件套里有断言失败，而你不知道为什么（**不许为了变绿而删断言**——断言是上一任
   修真事故留下的护栏，删了就是把修好的 bug 放回来）。
3. Actions 连续几轮红（质量门禁失败 / 推送失败）。
4. 学习通页面改版（作业抓不全、课程数偏离）——那是逆向适配的活。
5. 反爬升级的迹象：`meta.json` 里 `reason: no_courses` 或 `courses_failed > 0`
   **持续一整天**（偶发一两次是已知行为，系统会自己重试，不用管）。
6. 用户要的东西涉及新凭据、新权限、付费、对外发消息给第三方。
7. 你想改的东西会让某条 selftest 断言变红。

**上交时带上**：想做什么 / 已经试了什么 / 卡在哪一步 / 报错原文 / 你动过哪些文件
（`git diff` 贴出来）。信息越全，开发 AI 越快接手。
