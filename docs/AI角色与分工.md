# AI 角色与分工 —— 这个项目里的「两个 AI」

> **写给谁看**：用户本人（看懂自己的助手是怎么运作的）、接手的 AI（分清自己是谁、该读什么、能做什么）。
> 用户 2026-11-14 原话：「要分清这和前面那个是两个不同的 AI，一个是管开发的，一个是管日常更新的，
> 能力弱一点就按照 md 文档写的要求设置 AI 就好，写的尽可能详细，要保证人也能看懂。」
> 这份文档就是按这句话写的。

---

## 0. 一张表分清两个 AI

| | **🛠 开发 AI**（管开发） | **🤖 日常 AI**（管日常更新） |
|---|---|---|
| **它是什么** | 跟用户对话的那个 AI（Claude / GLM / 任何接手会话的模型） | GitHub Actions 每 20 分钟自动跑的程序（容器里的 Python + 被调用的 AI 接口） |
| **谁启动它** | 用户发消息 | cron 时间表（`assistant.yml` 的 `7-59/20`） |
| **活多久** | 一次会话 | 每轮几十秒，跑完容器就销毁 |
| **能力** | 强：能读仓库、改代码、改文档、跑验证、派发 Actions | 弱：只会按**设定文件**办事，不会自己发明动作 |
| **能改代码吗** | ✅ 能（这是它的本职） | ❌ **永远不能**（见 §3，四条理由） |
| **能收到用户消息吗** | ✅ 用户直接对它说话 | ❌ 收不到（webhook 单向，它发出去的消息你看不到回复渠道） |
| **它的「记忆」** | 会话上下文 + 仓库文档 | 没有。每轮都是全新的，状态全在 `data/*.json` 里 |
| **入口文档** | [AGENT.md](../AGENT.md) → [AI 运维手册](AI运维手册.md) → 本文 §2 | 本文 §3 就是它的全部「人生说明」 |

**一句话记住**：你（用户）只对**开发 AI**说话；**日常 AI**的行为你不直接指挥，
你想让它变一变，就对开发 AI 说，由开发 AI 去改设定文件。

---

## 1. 为什么必须分清（血泪教训）

这个仓库出过的事故，全部源于把两者搞混：

- **把日常 AI 当开发 AI 用** = 让一个没有判断力、没人监督的程序改代码。
  它一旦把隐私守卫改坏，泄露直接进公开 git 历史，抹除要动用 force push（本项目做过一次，代价极高）。
- **把开发 AI 当日常 AI 用** = 人不在场时项目停摆。日常 AI 的价值恰恰是**无人值守**：
  断网断电它不抱怨，AI 接口挂了它有降级文案，凭据它接触不到。
- 两者的验证标准也不同：开发 AI 改一行要过 **ruff + selftest + runner 实测**三道门；
  日常 AI 每轮的「验证」就是**日志里有没有预期关键字**（`[push] … 文案来源：AI`、`✅ 推送成功`）。

## 2. 开发 AI（管开发的）—— 你现在读的就是给你的

### 2.1 你的第一小时（按顺序）

1. 本文（知道自己是谁）；
2. [AGENT.md](../AGENT.md)（六条铁律 + 全部坑，一条不许违反）；
3. [AI 运维手册](AI运维手册.md)（改代码五步流程、逐功能验收清单、踩坑速查）；
4. [不足与风险](不足与风险.md) §0.5 状态表（唯一权威的完成度账本，防止把修好的再修一遍）；
5. [开发习惯](开发习惯.md)（16 条协作规则，每条附用户原话）；
6. 改动前跑门禁：`ruff check scripts --select E9,F63,F7,F82,F821,F401` + `python scripts/main.py selftest`。

### 2.2 你的职责

- **改代码与文档**：五步流程 = 定位 → 改 → 同步 selftest → 本地验证 → 推送 + runner 验证。
  没有日志证据不许说「验证通过」（见运维手册）。
- **改日常 AI 的设定**：用户说「晚安别提天气了」，你不是去回复日常 AI——
  你去改 `scripts/daily_push.py` / `scripts/prompts.py`，推上 main，下一轮日常 AI 自动按新设定跑。
- **替用户当守门人**：涉及凭据、隐私、force push、新自动化的事，必须用户明确授权才动手。

### 2.3 禁止事项（与 AGENT.md 铁律一致）

手改生成物 · 把凭据写进任何文件 · force push（历史清除需用户点名授权）·
改人格改到越界（PERSONA 的硬边界）· 把课表塞进推送（用户原话「课表的提醒我不用你」）·
把 plans.json 的计划播报回飞书（用户原话「随口写的不要发到飞书里」）。

## 3. 日常 AI（管日常更新的）—— 它的完整人生说明

### 3.1 它每一轮做什么（每 20 分钟，cron `7-59/20` → 模式 `tick`）

| 步 | 干什么 | 设定在哪 |
|---|---|---|
| 1 | 质量门禁（ruff + selftest），不过就整轮罢工 | `assistant.yml`「质量门禁」步 |
| 2 | 按 `data/runtime.json` 的时间戳决定该不该采集：study 60min / diary 120min / notice 360min | `main.TICK_INTERVALS` |
| 3 | 采集：学习通模拟登录 → Gitee 日记（名言+计划+写回复查）→ 6 个公告站 | `scripts/*_collector.py` + `data/sources.json` |
| 4 | 三时段推送判断（07/12/22 + 补发窗口 morning/noon 5h、night 2h） | `main.PUSH_HOURS` / `PUSH_CATCHUP_HOURS` |
| 5 | **6 小时紧急截止提醒**（剩余 <6h 且未交的作业，同一截止时间只提醒一次） | `daily_push.URGENT_HOURS`，记账 `runtime.urgent6` |
| 6 | 渲染 README / docs / 看板数据（零网络零 token） | `scripts/render_readme.py` + `*_template.md` |
| 7 | 提交数据到仓库（`git pull --rebase` + push，不 force） | `assistant.yml`「提交数据」步 |
| 8 | 发飞书：三时段卡片照发；**常规成功静默**（用户原话「正常运行的不用给我汇报」）；失败/紧急才报 | `scripts/notify_feishu.js` |

**触发来源有两路**（2026-11-15 定稿，用户明确「不能依赖外部的定时」）：**仓库内接力链**
（relay.yml 自续链，每 ~20 分钟一轮，主路）+ GitHub 自己的错峰 cron（`7-59/20`，兜底）。
两路并存无冲突：`pushed[kind]` 按日期记账，谁先触发谁发，**绝不重复推送**。
（cron-job.org 曾接入半天即停用：外部定时服务有日配额限制，不符合「不依赖外部」的要求；
其 API 用法留档在运维手册，供未来需要时参考。）

凌晨 00:00–06:00 窗口内它还会把挖出来的计划写回日记复选框（`scripts/diary_writeback.py`，
窗口在 `data/sources.json`，白天一次都不提交）。

### 3.2 它发消息的规则（全部来自用户原话，改前先读）

- 早报 = 问好 + 作业总览 + 公告总览 + 一言 + 图；午安 = 鼓励 + 新作业 + 7 天内截止 + 每日英语 + 名言回顾 + 一言 + 图；
  晚安 = 日记小结 + 48h 截止 + 本周盘点 + 明日预告 + 明早天气 + 一言 + 图。
- **作业允许跨时段重复**（用户原话）；公告只在早报；当天新名言只在晚安、历史名言回顾只在午安。
- **永不发**：课表（「课表的提醒我不用你」）、plans.json 的潜在计划（「随口写的不要发到飞书里」）。
- 已过时效的公告不发（截止已过或发布超 90 天，`utils.notice_stale()` 是唯一判定）。
- 人格只有一份：`scripts/prompts.py` 的 `PERSONA`（傲娇雌小鬼，损拖延不损人，硬边界写在里面）。
- AI 只写「人话」，清单由程序确定性拼接——**清单永远不经过 AI**，所以不会漏条目。

### 3.3 它绝对不做的事（边界，不是 bug）

1. **不自主改代码**。四条理由（详见 [AI 回复与自更新手册 §5.3](AI回复与自更新手册.md)）：
   公开日志人人可见、它接触凭据、没人审、会绕过门禁。
2. **收不到你的回复**（webhook 单向）。双向升级的三条路线都在手册 §4.3，**需用户点头才开工**。
3. **不主动发明任务**。它只做设定文件里写明的事——你觉得它「少做了什么」，
   那是设定如此；要改就找开发 AI 改设定。
4. 手动派发 `morning/noon/night` 是无副作用的测试（`daily_push` 不写记账，
   当天的正式推送照常）。用户 2026-11-15 明确：**测试卡片不算打扰，可以继续发**——
   所以开发 AI 验证推送格式时直接派发即可，不用绕道本地渲染。

### 3.4 「让 Actions 里的 AI 更新这个仓库」的准确含义

- **数据与生成物（README / docs / data）**：✅ **已经是全自动**——每轮 tick 采集后
  `github-actions[bot]` 自动 commit & push，这就是日常 AI 在「更新仓库」，无需任何人参与。
- **代码与文档**：❌ 日常 AI 不碰。这条路必须走开发 AI（人发起会话 → 改 → 门禁 → 推送）。
  将来若真要让日常 AI 做代码级小改动，护栏方案（白名单文件 + 强制门禁 + 开 PR 不直推）
  已写在 [AI 回复与自更新手册 §5.4](AI回复与自更新手册.md)——**未实现，用户明确授权前不开工**。

## 4. 两者的协作闭环（日常运转的全部）

```
用户发消息 → 开发 AI 改代码/设定 → 过门禁 → push main
     ↓
GitHub 每 20 分钟起容器 → 日常 AI 按新设定采集/推送/渲染 → 自动提交数据 → 飞书推给用户
     ↓
出问题 → 飞书红卡/README 状态区报警 → 用户找开发 AI 排查 → 循环
```

日常 AI 出错时的排查入口：GitHub Actions 日志（公开）→ `data/runtime.json` 的 `errors` →
[常见问题](常见问题.md) D 组 → [AI 运维手册 §8](AI运维手册.md) 踩坑速查。

## 5. 术语（给人看的）

| 词 | 人话 |
|---|---|
| **tick** | 日常 AI 的一班岗：每 20 分钟响一次的那趟巡逻 |
| **设定文件** | 决定日常 AI 行为的代码与配置（prompts.py / main.py 常量 / sources.json / assistant.yml） |
| **生成物** | 日常 AI 写的文件（README、docs 数据、week.svg），手改会被下一轮覆盖 |
| **门禁** | 干活前的两道检查（静态检查 + 离线自检 222 条断言），不过就不采集 |
| **降级** | AI 接口/图源/一言挂了时用确定性内容顶上，保证消息照发 |
| **记账** | `data/runtime.json`：发没发过推送、写过没写回、紧急提醒过谁——删掉即全部重置 |
