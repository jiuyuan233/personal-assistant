# 不足与风险

**这是一份诚实的自我审计，不是成绩单。** 用户要求「从整个项目来看，你认为还有什么不足、做的不好的地方也写到仓库里」，
所以这里把已知的缺陷、隐私风险、未验证的假设全部列出来，**包括开发过程中我自己造成的事故**。

写这份文档的规矩（和 [开发习惯](开发习惯.md) 一致）：

- 每条都给 **根因位置（`文件:行号`）+ 实测证据**，不写「可能」「大概」当结论。
- 严格区分三种状态：**已核实**（读过代码 / 量过数据）、**未验证**（有理由怀疑但没证据）、**等用户决定**。
- 行号会随代码变动漂移，**以函数名为准**，行号只是当时的定位线索。
- **本文档不写出任何真实学号、教师姓名、私人日记内容、凭据值。** 只描述类别与形状。
- 审计里有一条被夸大的说法，已在下面 §2.3 明确纠正 —— **不要把审计结论当事实照抄**。

审计时间：2026-11-13。数据快照：学习通 14 门课 / 38 条任务 / 5 条 pending，日记 63 条计划 / 15 条名言。

**共 31 条**：高危静默错误 5（§1）· 隐私 6（§2）· 数据质量 9（§3）· 工程运维 6（§4）· 显示与文档 5（§5）。
另有 §6「不是缺陷」10 项、§7「等用户决定」4 项。

---

## 0. 一句话总结

**功能层面用户提的六条要求都实现并 runner 实测过了；但「可靠性」和「隐私」两层明显欠账。**

最严重的三件事：

1. **定时触发至今 0 次生效** —— 整个项目的前提是「每 20 分钟自动跑」，而 65 次运行**全是手动派发**（§4.1）。
2. **学习通会「假成功」** —— 登录态中途失效时，README 显示「无作业」+「✅ 正常」，用户以为没作业（§1.1）。
3. **公开仓库里仍有别人的个人信息** —— 教师真实姓名、以及用户自己的私人计划全文（§2）。

## 1. 高危：会静默给出错误结果

这一类的共同特征是 **不报错、不告警、看起来一切正常**。比崩溃更危险。

### 1.1 学习通「假成功」：登录态失效 → 空清单 + ✅ 正常

- **根因**：`study_collector.py` 的 `is_tip_page()` 只认三种字符串（`<title>提示</title>`、`参数传递不正确`、`无权限的操作`）。
  会话中途失效时，超星返回的是 **HTTP 200 的登录页**，这三个都不匹配 → 当成正常页面解析 → `rows = []`。
- **后果**：`run()` 末尾无条件写 `"ok": True`，README 那门课显示「无」，数据源状态显示「✅ 正常」。
  **用户会以为真的没作业，从而错过截止时间。**
- **实测**：`is_tip_page()` 的判定集合只有 3 个字符串；`save_json(META_PATH, {... "ok": True ...})` 没有任何前置校验。
- **建议**：① `is_tip_page()` 增加登录页特征（`passport` / `登录` / `fanyalogin` 表单）；
  ② 一门课解析出 0 行时，与 `courses.json` 里上次的 `task_count` 比对，**从有到无要判为可疑而不是正常**；
  ③ `ok` 改成有条件：`courses_failed > 0` 或 `ok_courses < 期望值` 时至少降级为 `partial`。

### 1.2 一次 token 全失败 → 清空历史任务

- **根因**：`study_collector.py` 里 `mint()` 失败就 `continue`，14 门课全失败时 `all_tasks = []`；
  紧接着 `merge_tasks(load_list(TASKS_PATH), all_tasks, now)`。
  而 `dedup.merge_tasks()` 的语义是「**新列表就是权威列表**，没出现在新列表里的作业直接丢弃」。
- **后果**：`tasks.json` 被覆盖成空，历史任务全丢，`meta.ok` 仍是 `True`。
  这个设计本身没错（学习通列表页确实会淘汰过期项），**错在没有区分「真的没了」和「这次没抓到」**。
- **建议**：`ok_courses == 0` 时**直接 return，不落盘**；或 `merge_tasks` 增加「新列表为空且旧列表非空 → 拒绝合并」的守卫。

### 1.3 推送失败仍发绿卡

- **根因**：`.github/workflows/assistant.yml` 的飞书通知步骤用 `NOTIFY_STATUS: ${{ steps.execute.outcome }}`，
  但 **`git push` 在另一个步骤「提交数据」里**。推送失败时 `execute.outcome` 依然是 `success`。
- **实测**：workflow 里 `job.status` 出现 0 次。
- **后果**：数据没推上去，用户收到的飞书卡片却是绿的。
- **建议**：改成 `${{ job.status }}`（一行改动，收益最大）。

### 1.4 AI 抽取失败 → 该篇日记永久漏采（而且文档说反了）

- **根因**：`diary_collector.py` 的 `ai_extract()` 捕获异常后 `return [], []`；
  主循环紧接着**无条件**写 `known[rel] = {"sha": ...}`。
  增量判定靠 sha 差异（`changed = [e for e in entries if known[...].sha != e.sha]`），
  sha 已记为「处理过」→ **除非用户再编辑这篇日记，否则永远不会重试**。
- **文档矛盾**：[常见问题](常见问题.md) C3 写着「该文件不在 `files` 里 → 上次处理失败了，下次会重试」。
  **代码不是这样**：失败的文件也在 `files` 里。这条文档是错的，会误导排查。
- **建议**：`ai_extract` 返回空且原文非空时**不推进 sha**（或记 `failed: true` 并在下次强制重试）；同时修 C3 的措辞。

### 1.5 错过凌晨窗口 → 计划永久不再进入待办

- **根因**：`diary_writeback.pick_plans()` 的入选条件是 `first_seen == yesterday or pid in rolling`。
  `first_seen` 是**采集日期**（`merge_plans` 里 `setdefault("first_seen", today)`），不是日记里的日期。
  一条计划只在「被采集到的次日」有资格；`rolling` 只包含**已经写进去过**的计划。
- **后果**：凌晨三次窗口（北京 00:07 / 02:07 / 04:07）全部失败或全部被并发挤掉 → 这条计划**再也不会被写进任何一天的日记**。
  用户要求的是「13 号的潜在任务写进 14 号，15 号复查，没完成写进 15 号」—— **链条断在第一天就再也接不上**。
- **建议**：入选条件改成「`state == open` 且从未写回过」+ 一个 `written_once` 标记，而不是靠日期相等。
  日期相等这种写法对「跑一次就成功」的乐观假设太强。

## 2. 高危：隐私（这是公开仓库）

**判断标准只有一个：这个值能不能定位到一个具体的人。** 不是「看起来像不像敏感字段」。
这条标准是两次事故换来的，见 [开发习惯](开发习惯.md) 第 8 条。

### 2.1 教师真实姓名进入公开任务标题

- **实测**：`data/study/tasks.json` 里有一条考试标题以**教师真实姓名**开头（姓名 + 学年学期 + 课程名 + 结课测试），
  并已渲染进 [已剔除任务](已剔除任务.md)。
- **根因**：`utils.scrub_course_name()` 只清洗**课程名**，`parse_exam_rows()` 取到的**任务标题**没有任何清洗。
- **为什么没直接修**：标题格式必须**先实测再写正则**（这是本项目的硬规矩，猜正则已经踩过坑）。
  而且「删掉人名」很容易误伤正常课程名（`军事理论（同济大学版）` 这类）。
- **建议**：先 dump 若干条真实考试标题确认格式，再在**采集层**按确认过的形状清洗；
  或者更保守 —— 考试标题只保留课程名部分，丢弃前缀。**这条应该优先修，泄露的是别人。**

### 2.2 私人日记计划被原样公开

- **实测**：`data/diary/plans.json` **63 条计划、58 条 open，来自 20 个源文件**。
  其中**单个私人长期计划文件贡献 17 条**，另一个同主题文件贡献 5 条。
  每条都带 `source_file` 字段，**完整的私有仓库目录结构因此公开**（含用户标注为私人的重大个人决策主题）。
  这些内容同时出现在 README、[潜在计划](潜在计划.md) 和 `quotes.json` 里。
- **根因**：用户当初的要求是「gitee 可以读到我写的日记就可以」，采集范围是整个 `Tasks` 目录，
  **没有区分「愿意公开的日常」和「私人计划」**。开发时按字面实现了，没有就公开范围反问一句。
- **这是设计层面的欠账，不是代码 bug。** 修法有三种，需要用户选：
  1. 仓库改 private（最简单，但 Pages / 公开分享就没了）；
  2. `sources.json` 增加 `exclude` 路径黑名单，私人目录不采（**推荐**，保留公开看板）；
  3. 计划只公开文本、去掉 `source_file`（**治标不治本**，文本本身就是隐私）。
- **⚠️ 已公开的内容不会因为在源码里加了黑名单就消失**，历史提交里还在，见 §7。

### 2.3 一条吐槽被误判成计划（纠正审计的夸大说法）

- **实测**：`plans.json` 里有 1 条明显是情绪吐槽而非计划，`confidence = 1`（最低），`state = done`。
- **审计原话说它「会被写回成日记里的复选框」—— 这是错的。**
  `diary_writeback.pick_plans()` 第一件事就是 `if p.get("state") != "open": continue`，
  `state = done` 的条目**不会**被写回。
- **真实影响**：它只是脏数据，占一个计数，不会污染用户的日记。
  但它说明 `confidence` 阈值没有起到过滤作用 —— **低置信度的抽取结果照样入库**。
- **建议**：`merge_plans` 入库前加 `confidence >= 2` 门槛（阈值要实测调，别拍脑袋）。

### 2.4 学号泄露：修了三次，git 历史里还在

- **第一次**：上传的抓包 HAR 里含学号 → 文件已删、历史已抹（用户当时明确授权了一次 force push）。
- **第二次**：学习通把**同学学号**写进课程名，采集器原样存盘、原样渲染进公开 README →
  已在采集层加 `utils.scrub_course_name()`，runner 实测落盘数据学号残留 0。
- **第三次（我自己造成的）**：写第二次修复的文档时，为了「说清楚真实案例」，
  把**真实学号原样抄进了 6 个文件、23 处**（AGENT.md / CHANGELOG.md / 开发习惯 / 技术路径 / main.py / utils.py）。
  采集层洗干净了，文档层又漏一遍。**修复说明不是脱敏豁免区。**
- **现状**：已全部换成 `<学号>` 占位符；selftest 的测试数据改成**代码合成**（`str(9 * 10**7 + i)`），
  源码里不出现任何 7 位以上数字字面量。
  selftest 新增 **全仓库**扫描（不再只扫 `data/study/*.json`），两种形状：
  ① 逗号串起的长数字串 ② 汉字紧跟 7 位以上数字（**排掉 `20YYMMDD` 日期** —— 实测任务标题「作业20261022」是合法的）。
  本地用 Node 等价实现跑过：60 个文件、0 命中、日期反例不误报、合成学号正例命中。
- **⚠️ 仍未解决**：**第二、三次的真实学号都在 git 历史里**。当前 HEAD 干净 ≠ 历史干净。见 §7。

### 2.5 `cpi` / `enc` / `clazzid` 公开：可用性与隐私的取舍（未决）

- **实测**：README 与 [已剔除任务](已剔除任务.md) 里的作业深链带 `cpi`、`clazzid`、`enc` 参数（数十处）。
- **矛盾**：这些参数**足以定位到用户本人的教学班**；但去掉它们，作业链接就点不开了 —— 而「点进去直接做作业」是这个清单的核心价值。
- **没有擅自改**，因为这是产品取舍不是 bug。三个选项见 §7。

### 2.6 脱敏只覆盖 `utils.log()`，原始 stderr 直通公开日志

- **根因**：`utils.log()` 是唯一的脱敏闸口（`_REDACT_PATTERNS` 覆盖 access_token / Bearer / sk- / ghp_ / password 类键）。
  但 workflow 里是 `python scripts/main.py "$MODE" 2>&1 | tee -a /tmp/task-output.log`，
  **原始 stderr（含 Python traceback）绕过了这个闸口**；通知步骤又 `tail -200` 把它发进飞书。
- **放大因素**：**仓库是 public → Actions 运行日志也是 public。** 任何未脱敏的异常文本都是公开可见的。
- **另一个缺口**：`_REDACT_PATTERNS` **没有 Cookie / JSESSIONID 规则**。学习通链路大量依赖 Cookie，
  一旦 `requests` 抛出的异常里带上请求头，就是明文。
- **建议**：① 加 Cookie / JSESSIONID / `_uid` / `UID` 脱敏规则；
  ② 通知步骤发送前再过一遍脱敏（`notify_feishu.js` 里做，不要只依赖 Python 侧）；
  ③ traceback 只发类型与最后一行，不发完整栈。

## 3. 中危：数据质量与判定

### 3.1 公告标题通道绕过 `deadline_supported()` → 幻觉日期永久固化

- **根因**：`notice_collector.py` 有两条 AI 通道。
  **正文通道**做了双重校验（格式 + `deadline_supported(text, dl)` 语义/字面依据），不合格就丢弃；
  **标题打分通道**只做了 `re.fullmatch(r"\d{4}-\d{2}-\d{2}", dl)` —— **格式对就收**。
- **放大因素**：`dedup.merge_notices()` 是「旧值优先」，`_carry()` 只补空字段
  （`if not old.get(k) and new.get(k)`），正文通道又是 `elif not n.get("deadline")`。
  → **标题通道一旦写进一个幻觉日期，后面任何通道都改不掉它。**
- **为什么严重**：项目里早就知道「提示词拦不住日期幻觉」，所以才写了 `deadline_supported()` 这道代码守卫。
  **守卫只装了一半的门。**
- **建议**：标题通道也过 `deadline_supported()`（拿标题当 text），或者干脆**不允许标题通道写 deadline**。

### 3.2 勾了又取消 → AI 来源的计划永久 done

- **根因**：`diary_collector.py` 把写回复查到的勾选结果写成 `p["state"] = "done"`，**但不改 `origin`**。
  `dedup.merge_plans()` 里：`origin == "checkbox"` 的会跟着复选框变（`[x]` 改回 `[ ]` 能复原），
  但紧接着 `if old.get("state") == "done": continue` —— **AI 来源的计划一旦 done 就短路，永远不再更新**。
- **后果**：用户在助手区块里误勾了一条，再取消勾选，**它永远不会回到待办**。
- **实测**：63 条计划里 38 条 `origin=checkbox`、25 条 AI 来源；后者全部适用这个缺陷。
- **建议**：写回标记完成时把 `origin` 改成 `checkbox`（复选框已成为权威来源），或在 done 短路前先判 origin。

### 3.3 名言点评不回填

- **实测**：`quotes.json` **15 条名言，只有 8 条有 `comment`**，7 条空着。
- **根因**：`merge_quotes()` 按正文去重，命中已有条目时走 `_carry(..., ("comment",))` —— 只补空。
  但增量采集只处理 **sha 变化的文件**，老日记不再重跑 AI，**空 comment 就永远空着**。
- **后果**：用户要求「名言那一块加上 AI 的点评」，实际上**近一半没有点评**。功能只做了一半。
- **建议**：加一个 `backfill` 模式，专门给 `comment` 为空的名言补点评（一次性，跑完即可）。

### 3.4 计划 / 名言无淘汰，截断无提示

- **实测**：58 条 open 计划，README 只显示 15 条（`PLAN_LIMIT`），写回上限 20 条（`max_writeback`）。
  `merge_plans()` / `merge_quotes()` **没有任何淘汰逻辑**，只增不减。
- **后果**：① 数据无限增长；② **用户看不到「还有 43 条没显示」**，会以为计划就这么多；
  ③ 排序靠 `due_date`，而多数计划没有 due_date → 实际按 `first_seen` 排，**新计划挤掉老计划，老计划永远轮不到**。
- **建议**：截断处显示「另有 N 条，见完整文档」；给 open 计划加「超过 X 天未写回则降级/归档」的规则（X 要问用户）。

### 3.5 详情页预算按遍历序取，不按紧急度

- **根因**：`study_collector.py` 里 `need = [t for t in all_tasks if t["state"] == "pending"][:detail_budget]`，
  `detail_budget` 默认 8。`all_tasks` 是**按课程遍历顺序**拼起来的。
- **后果**：排在后面的课里有一条 1 小时后截止的作业，**可能拿不到精确截止时间**，
  只能用列表页倒计时反推（标 `≈`）—— 而**逾期判定依赖精确截止**。
- **建议**：取详情页前先按反推截止时间排序，**紧急的优先**。

### 3.6 14 门课没有期望值守卫

- **根因**：`courses = cx.list_courses()[:max_courses]`（默认 40），只判 `if not courses`。
- **后果**：用户明确说「我一共 14 个课」，但**抓到 3 门也算成功**。页面结构变化导致漏抓时无人发现。
- **建议**：`sources.json` 里加 `expected_courses: 14`，实际数量偏离就告警（不是硬失败，选课会变）。

### 3.7 考试 / 互评基本空转，exam 链接不是深链

- **实测**：38 条任务里非作业只有 10 条 —— **5 条考试全 done、4 条互评 done、1 条互评 pending**。
  而那 1 条 pending 的互评窗口是 `2026-11-10T23:01+08:00`（精确），**今天 11-13，早已逾期**，会被剔除。
  → **考试与互评这两条解析链路目前产出 0 条可做任务。**
- **链接问题**：`parse_exam_rows()` 拼的 url 是**课程级 `exam-list` 页**，不是具体某场考试，且没带 `enc`/`stuenc`。
  **能否打开未实测**（需要登录态），所以这里只说「不是深链」，不说「死链」。
- **建议**：要么补全考试深链参数并实测，要么承认这条链路当前无产出、降低它的优先级，别让它每轮白跑。

### 3.8 无数据过期告警；失败覆盖 meta 抹掉 `last_success`

- **根因**：`render_readme.render_alert()` 只产出两种告警（🟠 今天有截止 / ⚠️ 学习通未同步），
  **没有「数据已经 N 小时没更新」的告警**。
  而 `study_collector.py` 的三个失败分支都用**全新 dict** 覆盖 `meta.json`，
  里面没有 `last_success` 字段 → **上一次成功的时间被抹掉了**，事后无法判断数据有多旧。
- **建议**：失败时**读取旧 meta 再合并**，保留 `last_success`；`render_alert` 增加数据年龄告警（阈值建议 3 小时）。

### 3.9 缺创新创业学院公告源

- **实测**：`data/sources.json` 的 notice 列表有 5 项（校网通知、教务处、教务处活动通知、校团委、招生就业处<已禁用>），
  **没有创新创业学院**。
- **为什么算不足**：用户当初同意的绕登录方案原话是「改抓校团委/教务处/**创新创业学院**的公开公告页」。
  **三个里只做了两个**，而创新创业学院恰好是竞赛信息最集中的地方。
- **建议**：找到该校创新创业学院的公开公告页 URL，实测可抓后加进 `sources.json`（这是手工可编辑文件）。

## 4. 中危：工程与运维

### 4.1 ⚠️ 定时触发至今 0 次生效 —— 项目前提未成立

- **实测**（GitHub API，2026-11-13）：
  - `actions/runs?per_page=1` → `total_count = 65`
  - `actions/runs?event=schedule&per_page=1` → **`total_count = 0`**
  - 仓库：`default_branch=main`、`fork=false`、`private=false`、`archived=false`、`disabled=false`、
    `created_at=2026-11-13T04:35:59Z`
  - workflow：`个人助手` → **`state=active`**
  - `on.schedule` 块语法正确，8 条 cron 都在默认分支上，含 `*/20 * * * *`
- **也就是说**：仓库建了 6 小时以上，`*/20` 本该触发约 19 次，**实际 0 次**。
  所有 65 次运行都是 `workflow_dispatch`（我手动派发的）。
- **原因未定位。** 已排除：语法错误、workflow 被禁用、fork、非默认分支、仓库归档。
  剩下的可能：GitHub 侧调度延迟/丢弃（官方文档承认整点高负载会延迟）、新仓库调度索引尚未生效、
  仓库级 Actions 权限设置。**`GET /repos/.../actions/permissions` 需要认证，当前 shell 没有 PAT，查不了。**
- **下一步诊断**（谁有 PAT 谁跑）：
  1. `curl -H "Authorization: Bearer $GH_PAT" .../actions/permissions` 看 `enabled` 与 `allowed_actions`；
  2. **停止手动派发**，等一个完整小时过去，再查 `event=schedule`；
  3. 24 小时后仍为 0 → 去 Settings → Actions → General 核对，并考虑 GitHub 对新仓库的调度节流。
- **为什么这条排第一**：用户要的是「每 20 分钟自动爬」。**在 schedule 真正跑起来之前，这个项目只是一个手动脚本。**
  所有「自动化」的验证结论都建立在手动派发上，**不能等同于定时链路已验证**。

### 4.2 每 20 分钟产生纯时间戳提交

- **根因**：`dedup.save_list()`、`schedule_parser` 的三个落盘、`render_readme` 的 `docs/data/*.json`
  都无条件写 `updated_at = 现在`。**内容完全没变，时间戳也变** →
  workflow 里 `if git diff --cached --quiet` 的「无更新跳过提交」分支**永远不会命中**。
- **实测**：`git rev-list --count origin/main` = **80**，其中 **76 个集中在最近 6 小时**。
- **后果**：提交历史被噪声淹没，真正有意义的变更找不到；仓库体积无谓增长。
- **建议**：`updated_at` 只在**内容真的变了**时更新（先比对去掉时间戳后的哈希），
  或者把时间戳挪出被提交的文件（放进不落盘的运行日志）。

### 4.3 并发组只保留 1 个 pending，吃掉凌晨重试

- **根因**：`concurrency.cancel-in-progress: false` **并不等于「全部排队」** ——
  GitHub 同一组里**只保留一个 pending**，后到的会把先到的挤掉。workflow 注释里已经写明了这一点。
- **后果**：① 凌晨三次写回重试可能被排队的采集任务挤掉，**三次机会实际只剩一次**（叠加 §1.5 就是永久丢计划）；
  ② **被挤掉的 run 根本不会启动 job，`if: always()` 的通知步骤也就不会执行 → 用户收不到任何失败提示**。
- **建议**：写回单独一个并发组（现在只区分了 push / collect）；或给凌晨窗口留出不与采集重叠的时段。

### 4.4 除离线 selftest 外没有任何质量门

- **实测**：workflow 里 `ruff` / `mypy` / `pytest` / `flake8` / `npm test` **出现 0 次**。
  唯一的质量保障是 `mode=selftest`（**107 条断言，0 失败**，runner 实测），而它**只在手动派发时跑**。
- **另一个缺口**：`mode=probe` 只测**连通性**，不测**解析正确性**。
  站点改版导致正则失配时，probe 全绿，采集静默返回空（正是 §1.1 的入口）。
- **建议**：① 把 selftest 挂进 `finalize` 的前置步骤（它是零网络零 token 的，代价极低）；
  ② probe 增加「解析出的课程数 / 任务数是否 > 0」断言；③ 加 ruff（纯静态，秒级）。

### 4.5 缺 `AI_API_KEY` 时推送直接崩，不降级

- **根因**：`ai_client.AIClient.__init__` 用 `env("AI_API_KEY", required=True)`，
  而 `utils.env()` 在 required 缺失时调 **`sys.exit(1)` → 抛 `SystemExit`**。
  `daily_push.run()` 的兜底是 `except Exception` —— **`SystemExit` 继承 `BaseException`，捕不到**。
- **后果**：写好的 `fallback_message()` 降级文案**根本不会被用到**，整个推送步骤死掉。
- **对比**：`diary_collector.py` 就处理对了（`except SystemExit` 单独捕获后降级为「只做复选框解析」）。
  **同一个坑，一处填了一处没填。**
- **现状**：`AI_API_KEY` 已配在 Secrets 里，所以这是**潜在缺陷，当前没有触发**。
- **建议**：`daily_push` 改 `except (Exception, SystemExit)`，或 `AIClient` 不 `sys.exit` 改抛普通异常。

### 4.6 日记写回从未真实执行过

- **实测**：所有写回相关的验证都是**离线 selftest + 窗口守卫逻辑**，
  **真实的 Gitee create / update 调用一次都没发生过**（窗口守卫 fail-closed，白天只复查不写）。
- **首次自然写入**：北京时间 **2026-11-14 00:07**，目标 `日/2026-11-14.md`。
- **风险**：Gitee API 的「文件不存在返回 200 + `{}`」这个坑已经在读路径上处理了，
  但**写路径（POST 创建 / PUT + sha 更新 / sha 冲突重试）在真实仓库上未验证**。
- **建议**：14 号早上第一件事就是核对那次写回的结果，**不要假设它成功了**。

## 5. 低危：显示与文档

### 5.1 SVG 双红线，且 Pages 未开 → 实时线从未在浏览器里跑过

- **根因**：`week_svg.py` 在图里**烘焙**了一条红色当前时间线（finalize 时刻，20 分钟精度）；
  `docs/index.html` 用 `<img src="week.svg">` 显示它，再叠一个 DOM 元素 `#nowline` 由 `app.js` 每 30 秒移动。
  **`<img>` 里的线无法被 JS 隐藏** → 页面上同时存在两条位置不同的红线。
- **文档已承认这个设计**（index.html 的说明文字写了「图里的线每 20 分钟重画一次，这条覆盖线由浏览器实时移动」），
  但**视觉上就是两条线，会让人困惑哪条是真的**。
- **更关键**：仓库 `has_pages = false`，**Pages 没开 → 这个网页从未在真实浏览器里跑过**。
  `app.js` 的实时线、跨周隐藏逻辑、分组视图**全部只有代码，没有运行证据**。
- **建议**：开 Pages（需要用户同意）后实测；把 SVG 里那条烘焙线去掉，或改成浅色参考线，只留 JS 那条。

### 5.2 文档与代码不符（五处）

| 1 | [工作原理](工作原理.md)、[常见问题](常见问题.md)、[数据结构](数据结构.md) 三处引用 `render_readme.bucket_tasks`，并描述四桶分类（overdue / today / week / later） | **全仓库 scripts 里搜不到 `bucket_tasks`**（0 命中），当前实现不是四桶 | 未修 |
| 2 | 工作原理：「顶部告警按优先级只出一个：🔴 有逾期 > 🟠 今天有截止 > ⚠️ 学习通未同步」 | `render_alert()` **只有 🟠 和 ⚠️**，没有 🔴 | 未修 |

  文档里写着一个不存在的函数，下一个 AI 会去找它、找不到、然后可能自己造一个 —— **错误会繁殖**。
  第 3、4 条更直接：用户以为日记每 20 分钟更新，实际一天 7 次，**预期落差会造成误判**。

### 5.3 课表源文件污染课程名 + 嵌套加粗

- **实测**：`assets/WakeUp导入课表.ics` 的 186 条 `SUMMARY` 里，**10 条带时钟前缀的非课程事件**
  （形如「某时刻 + 例会名 + 课程名」被拼成了一个字符串），已原样渲染进 README 的课表表格。
  **污染在源文件里就有**（WakeUp 导出时把非课程事件混进了课程字段），不是解析器造出来的，但**我们没清洗**。
- **另一处**：README 里出现 `**第 **10** 周 / 共 18 周**` —— **嵌套加粗，Markdown 渲染会坏**。
- **建议**：课表解析时剥掉时钟前缀与明显的非课程事件；周次那处去掉内层 `**`。

### 5.4 `now` 取得过早 → 反推截止时间系统性偏早

- **根因**：`study_collector.run()` 在**循环开始前**取 `now = now_bj()`，
  而循环里每门课 `sleep(0.3)` 加上网络往返，14 门课要几十秒。
  列表页的截止时间是「`now` + 倒计时剩余」反推的 → **越靠后的课，反推结果越早**。
- **影响**：几十秒量级，**不足以造成误判逾期**（除非正好卡在边界），所以列为低危。
- **建议**：反推时用**当次请求返回的时刻**，而不是循环开始前的 `now`。

### 5.5 `sort_by_deadline()` 剥时区而不是换算

- **根因**：`dedup.sort_by_deadline()` 用 `dt.replace(tzinfo=None)` 排序。
  当前所有截止时间都是 `+08:00`，**剥掉后比较结果一致，所以现在没问题**。
- **风险**：一旦有 UTC 字符串混进来（比如某个接口返回 `Z` 结尾），**排序会差 8 小时**，而且是静默的。
- **建议**：改成 `dt.astimezone(BJ)` 再比较，从根上消除这类隐患。

## 6. 不是缺陷 —— 已核实正确，别乱改

审计同时确认了下面这些**做对了的地方**。列出来是为了防止下一个 AI「顺手重构」把对的改坏。

- **14 门课全部出现在 README**，没作业的写「无」；按活跃度（作业发表数量）降序；任务按截止时间近 → 远。
  以**课程列表**为全集遍历，不是以作业为全集。（实测 14 门 / `task_count` 合计 38 = 任务总数 38）
- **课程身份是 `(course_id, class_id)` 复合键**（`course_key()`）。同一门课挂两个教学班时不会串任务。
- **凌晨窗口 fail-closed**：窗口外只复查（只读），绝不提交，且不推进 `last_date`，跨午夜处理正确。
- **助手区块外的用户编辑零改动**；`strip_assistant_block()` 防止把自己的输出当输入再抄一遍。
- **sha 冲突会重读重试一次**，不覆盖用户刚写的编辑。
- **任务 ID 不含 `enc`**（enc 会过期，含进去会导致同一作业反复被当新任务）。
- **公告 120 天淘汰**（`NOTICE_KEEP_DAYS`）—— 这是唯一有淘汰逻辑的数据类型。
- **正文通道 `deadline_supported()` 做语义 + 字面双重校验**，拦得住日期幻觉。（标题通道没装，见 §3.1）
- **竞赛日历附录 269 项**：0 编号断档、0 重复、0 排序倒置，96 项有开始月、101 项有来源链接、173 项标「待核实」。
- **selftest 107 条断言全绿**（runner 实测），含「一周规则已废除」的回归守卫、隐私守卫、文档链接守卫、占位符守卫。

## 7. 等用户决定（我没擅自动）

### 7.1 要不要 force push 抹掉历史里的学号

- **现状**：当前 HEAD 已干净，但**第二、三次泄露的真实学号仍在 git 历史里**，公开仓库任何人可查。
- **矛盾**：[AGENT.md](../AGENT.md) 铁律 3 **禁止 force push**。

- **代价**：重写历史会让所有已有 clone 失效；如果有 fork 或 Pages 缓存，旧内容可能仍在。
- **选项**：① 授权一次 force push 彻底抹除（推荐，泄露的是别人的信息）；
  ② 仓库改 private（历史仍在，但不再公开）；③ 接受现状（不推荐）。

  ③ 深链只放在 private 仓库 / 本地，公开版只给标题（最安全，最不方便）。
- **这是产品取舍，不是 bug，所以等用户选。**

### 7.3 私人日记计划的公开范围

见 §2.2 的三个选项。**这一条建议尽快决定** —— 每多跑一轮采集，公开内容就多一批。
