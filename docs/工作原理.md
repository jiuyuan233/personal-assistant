# 工作原理

一次运行从 cron 到飞书卡片发生了什么。技术选型的**理由**在 [技术路径.md](技术路径.md)，这里只讲**流程**。
**「卡片是怎么拼出来的、AI 负责哪一段、想改话术动哪里」**在 [AI回复与自更新手册.md](AI回复与自更新手册.md)。

## 0. 调度：一个 workflow，一条 cron，频率写在 Python 里

`.github/workflows/assistant.yml` 只挂 **一条** cron：`*/20 * * * *` → 模式 `tick`。
`scripts/main.py` 的 `do_tick()` 读 `data/runtime.json` 里各模式的上次成功/上次尝试时间，
决定这一轮该跑什么：

| 干什么 | 间隔 | 判定依据 | 联网 | 花 token | 提交文件 |
|---|---|---|---|---|---|
| `study` 学习通 | 60 分钟 | `runtime.last_ok.study` / `last_try.study` | 学习通 | ❌ | data |
| `diary` 日记 | 120 分钟 | 同上 | Gitee API | ✅ | data（+ 凌晨写回用户日记仓库） |
| `notice` 公告 | 360 分钟 | 同上 | 学校公告站 | ✅ | data |
| `morning` 飞书早报 | 每天 07:00（北京） | `runtime.pushed.morning == 今天?` | 一言 + 二次元图 + AI | ✅ | 不提交 |
| `noon` 飞书午安 | 每天 12:00 | 同上 | 一言 + AI | ✅ | 不提交 |
| `night` 飞书总结 | 每天 22:00 | 同上 | 一言 + AI | ✅ | 不提交 |
| `finalize` 渲染 | **每轮都跑** | 无条件 | ❌ | ❌ | README + docs |

判定留 **5 分钟宽限**（`TICK_SLACK_MIN`）：Actions 的 cron 经常晚几分钟，
不留宽限的话「每小时一次」会漂移成「每 75 分钟一次」。

**失败也按同样的间隔重试**：`last_try` 和 `last_ok` 都参与判定。
否则登录链一直失败时会每 20 分钟重跑一次，把 AI 额度和账号风控一起烧掉。

**推送按日期记账，不按小时**：`runtime.pushed[kind]` 存的是 `YYYY-MM-DD`，
所以每种每天最多发一次；整点错过后在 **`PUSH_CATCHUP_HOURS[kind]` 小时内补发**
（morning 5h、noon 5h、night 2h），超过就不发了 —— 晚上 10 点的总结拖到凌晨毫无意义，还会吵醒用户。
窗口按时段给是因为实测 cron 两次触发间隔可达 4 小时 40 分，全局 3 小时会整段漏掉（见 [不足与风险](不足与风险.md) §4.1）。

**凌晨写回有强制加跑**：`diary` 的 120 分钟间隔不保证落在 6 小时写回窗口里，
所以 `do_tick()` 额外判断「现在在 `writeback_window` 内 且 `runtime.writeback_date != 今天`」，
命中就把 `diary` 塞进本轮待跑列表。

### 为什么从八条 cron 改成一条

原来 8 条 cron 靠 `github.event.schedule`（cron 表达式原文）分派模式。
**实测连续 1 小时 33 分钟一次都没触发**（详见 [不足与风险](不足与风险.md) §4.1）：
GitHub 对同一 workflow 的 schedule 有节流，条数越多越容易被丢；
而并发组只保留一个 pending，开发期 69 次手动派发把定时班反复挤掉。
改成一条之后，「几点该跑什么」变成 Python 里的纯函数 `due_collectors()` / `due_pushes()`，
**离线 selftest 就能验证**，日志里也能看到「本轮采集 [...] · 推送 [...]」，不再靠猜。

### 为什么写回只在凌晨

用户白天在 Obsidian 里写日记，白天往他的仓库提交会和他的编辑撞车。
守卫在**代码里而不是 cron 里** —— `diary_writeback.in_window()` 按
`data/sources.json` 的 `writeback_window`（当前 `00:00-06:00`，北京时间）判定，
窗口外直接返回 `skipped=outside_window`，一次提交都不发，只复查勾选。
这样即使手动派发 `diary`、或者 Actions 延迟到白天才跑，也不会写进用户的日记。
窗口从 5 小时放宽到 6 小时，是为了配合 tick 的 120 分钟间隔留出至少 3 次机会。

### 并发与手动派发

**只有一个并发组 `pa-run`**，`cancel-in-progress: false` —— 宁可排队也不打断正在写数据的那次。
拆成 push / collect 两组反而会让采集和渲染同时改 README，rebase 必冲突。
job 上有 `timeout-minutes: 25` 兜底：一个卡死的 run 会堵住整条队列。

**⚠️ 同一个 group 只保留一个 pending run。** 一次性派发多个模式，后派发的会把先派发的
**直接 cancel**（实测两条 CANCELLED）。**手动派发必须串行，等上一个 completed 再派下一个。**

`workflow_dispatch` 可手动指定 14 个模式：
`tick` / `finalize` / `diary` / `study` / `notice` / `schedule` / `all` / `backfill` /
`probe` / `studydiag` / `selftest` / `morning` / `noon` / `night`。

### 质量门禁（在执行之前）

```bash
ruff check scripts --select E9,F63,F7,F82,F821,F401
python scripts/main.py selftest
```

**门禁不过就不采集。** 这是为了避免带着 `NameError` 跑完一整轮登录链、最后静默写出空数据。
`F821`（未定义名字）这一条就能抓住「用了 `BJ_TZ` 却忘了 import」这类事故 ——
本项目真发生过一次，靠 runner 往返才发现，代价是一整轮采集。
selftest 里还有「文档引用的函数必须真实存在」「文档不许写着过时频率」两条守卫，
所以**改代码忘了改文档，门禁会直接红**。

## 1. 采集层（只有三个模式联网）

### study：学习通四步链

```
① POST passport2.huuc.edu.cn/fanyalogin
     uname / password 都要 AES-128-CBC 加密（key = iv = u2oh6Vu^HWe4_AES，PKCS7，base64）
     先 GET /login?fid=12 拿 cookie，再带 X-Requested-With: XMLHttpRequest
② GET  mooc2-ans.huuc.edu.cn/visit/courses/list      → 14 门课的 courseid/clazzid/cpi（实测去重后）
③ GET  mooc1.huuc.edu.cn/visit/stucoursemiddle       → 跟 302，从落地页抽 #enc / #workEnc / #examEnc
④ GET  /mooc2/work/list?courseId=&classId=&enc=<workEnc>          → 作业 + 互评
   GET  /exam-ans/mooc2/exam/exam-list?courseid=&clazzid=&enc=<examEnc> → 考试
```

③ 是**每门课都要重做一次**的：enc 是一次性令牌，不能跨课复用，也不能存起来下次用。
④ 两个接口参数大小写不同（作业 camelCase，考试全小写），搞混就返回「参数传递不正确！」。

解析出的每条任务算一个稳定 ID（`course_id|class_id|kind|work_id|answer_id` 的 md5，**不含 enc**），
截止时间 = 抓取时刻 + 页面倒计时（列表页不给绝对时间）。每门课之间 sleep 0.3s。

### diary：Gitee 增量

不 clone，走 API v5 `GET /repos/{repo}/contents/{path}`（中文路径必须百分号编码进 **URL 段**，不能用 `?path=`）。
递归列出 Tasks 下所有 `.md`，拿每个文件的 **git blob sha** 和 `data/diary/state.json` 里的比对：
sha 变了才处理，没变直接跳过。按文件名倒序（新的先处理），单次上限 `max_files_per_run`。

每个变更文件走**两条并行通道**：

- **确定性通道**：正则抓 Obsidian 复选框 `- [ ]` / `- [x]` → `origin: "checkbox"`，`confidence: 1.0`
- **AI 通道**：整篇喂模型 → 名言（逐字引用）+ 潜在计划（复选框里已有的**不许重复输出**）→ `origin: "ai"`

只有处理成功的文件才写回 state，失败的下次自动重试。

### notice：公开公告页

零登录。抓 `data/sources.json` 里 enabled 的站点，跟「下页」链接翻页（列表是**倒序**的，第一页最新）。
每条公告抽标题（优先 `title` 属性，教务处会截断可见文本）+ 发布日期 + 绝对 URL。

日期抽取有个坑：日期常在 `<a>` **外面**（前一个兄弟节点），所以要回看 200 字符；
而回看窗口可能命中**上一条**公告的日期，因此取「最靠近链接的那个匹配」（`m.end()` 最大），不是第一个匹配。

然后两道关：

1. **关键词门**：`block` 命中直接丢（放假/调课/党建…），`gate` 命中才进入候选，上限 30 条
2. **AI 打分**：每批 10 条，输出 0–5 分 + 分类 + 理由 + 截止日期。没配 key 或调用失败 → 退回纯关键词打分（boost=3 / gate=2）

### schedule：课表（离线）

读 `assets/WakeUp导入课表.ics`。WakeUp 的三个特点决定了处理方式：
每周一个 VEVENT、`RRULE:FREQ=WEEKLY;COUNT=1`（所以不用展开循环规则）、`DTSTART` **不带时区**（按北京时间解释）。

学期第一天不是配置项，是反推的：每条 event 算 `date - weekday天 - (week-1)*7天`，取众数 → `2026-09-07`。
节次靠一张 11 节的作息表精确匹配起止时间。

**`finalize` 每次都会重跑课表解析**，因为它是纯离线的、代价可忽略，而教学周必须每天前进。
否则 `current_week` 会停在最后一次手动跑 `schedule` 的那一周。

## 2. 合并层：两种相反的策略

`dedup.py` 是整个项目最容易改错的地方。核心判断：**这份数据的旧值和新值，哪个更可信？**

| | 公告 notices | 任务 tasks |
|---|---|---|
| 策略 | **旧值优先** | **新值优先** |
| 为什么 | AI 每天重打分，描述/评分会抖动；标题日期是客观事实，不该被覆盖 | 倒计时每小时都在变，旧值就是错值 |
| 例外 | `score` **只升不降**（避免好机会被误降后消失） | 旧记录有 `deadline_exact` 而新的没有 → **保留旧的精确值** |
| 清理 | 超过 120 天丢弃 | 不丢（已完成的进 README 折叠块） |

名言按**文本**去重（同一句话出现在多天日记里只留一条）；计划按 `text + source_file`。

计划的三条保护规则（优先级从高到低）：

1. 旧记录 `state == "cancelled"` → 直接跳过。**人工否决优先于一切**
2. 新记录 `origin == "checkbox"` → 无条件采用新 state。你在 Obsidian 里把 `[x]` 改回 `[ ]`，程序必须跟着改
3. 旧记录 `state == "done"` → AI 不能把它重新打开

## 3. 渲染层：零网络、零 token

`render_readme.py` 只读 `data/`，不 import 任何采集器，也不 import `ai_client`。这是结构上的保证。

1. `actionable()` 先按 `drop_reason()` 剔除**非待完成**和**已逾期**两类，判定与
   [已剔除任务](已剔除任务.md) 共用同一个函数，两处口径不会漂。
   剩下的按课程分组（`course_rows()`），课程顺序 = 活跃度（作业发表数量）降序，
   **没任务的课也列出来写「无」**。课程身份是 `course_id + class_id`，不是只有 course_id。
2. 计数分四档：`today` / `week`(7天内) / `later`(更远) / **`unknown`(截止未知)**。
   `unknown` 是独立一档，**绝不混进「更远」** —— 那正是用户报的 bug：
   抓不到截止时间的作业被显示成「还很宽裕」，其实早已逾期。
   表格里这类任务的截止列写 `⚠️截止未知`，顶部出 🔴 告警。
3. 填 `readme_template.md` 的 `{{占位符}}` → 写 `README.md`。
   非精确截止时间后面加 `≈`；公告与潜在计划**内嵌精简版**（5 / 8 条），
   同时各自渲染一份全量独立文档，节标题下链过去。**两处共用渲染函数，靠 `link_prefix` 区分链接基准。**
4. 顶部告警 `render_alert()` **按优先级只出一个**：
   🔴 采集失败 → 🔴 截止未知 → 🟠 今天有截止 → 🟠 有逾期被移出 →
   ⚠️ 部分降级 → ⚠️ 数据超过 3 小时未更新 → ⚠️ 未同步。
5. `week_svg.py` 手写 SVG 周课表（7 列 × 11 节，无图形库），今天的列高亮。
   图里那条**浅灰虚线**只是生成时刻的参考位置；红色「现在」那条由网页 JS 每 30 秒移动，
   几何参数从 `docs/data/schedule_geo.json` 读，两边共用一套算法。
6. 把前端要用的数据裁剪进 `docs/data/*.json`（GitHub Pages 只能伺服 `docs/`）。
   计划与名言的副本会**去掉 `source_file`**：那是私有日记仓库的目录结构。
7. 所有 JSON 落盘走 `save_list()` / `save_json_stable()`：**内容没变就不动 `updated_at`**，
   否则每小时一次采集即使一条数据都没变也产生一行 diff，每天白烧 24 个噪声 commit。

## 4. 提交

```bash
git add data docs README.md
git diff --cached --quiet && exit 0     # 没变化就不产生空提交
git pull --rebase origin <ref>
git push                                # 不带 --force
```

`probe` / `selftest` 模式跳过这一步（它们不该改数据）。
推不上去就让这步**失败**，飞书报红，人来处理——绝不用 force push 掩盖冲突。

## 5. 飞书通知（`if: always()`）—— 两条路

workflow 的飞书步骤先看 `/tmp/push-message.txt`：

```bash
if [ -s /tmp/push-message.txt ]; then
  node scripts/notify_feishu.js "$(cat /tmp/push-message.txt)"   # 卡片：三时段人格消息 + 清单 + 图
else
  node scripts/notify_feishu.js                                  # 卡片：运行状态（受降噪闸门约束）
fi
```

**路 A：三时段推送（morning / noon / night）**
`daily_push.py` 拼事实 → 取一言 → AI 写**人话**（失败则确定性降级）→
`info_block()` 确定性追加**作业 / 公告 / 一言** → 写进 `/tmp/push-message.txt`；
`anime_image.py` 另写 `/tmp/push-image.json`，由 JS 追加到卡片。
**AI 只负责 prose，用户点名要的内容不经过 AI，所以永远不会被漏掉或改写。**
执行步骤开头 `rm -f /tmp/push-message.txt /tmp/push-image.json` **两个都清**，
**所以推送模式崩在写文案之前时，会自动落到路 B 报红**，不会静默成功。

图片双路径：配了 `FS_APP_ID`/`FS_APP_SECRET` → 上传换 `image_key` → 卡片内嵌 `img` 元素；
没配 → 卡片带「点开今天的图」按钮（外链 Pixiv）。**两条路都不影响文字内容送达。**

**路 B：运行状态卡片（采集 / finalize / selftest / probe）**
`notify_feishu.js` 读 `/tmp/task-output.log` 的最后 200 行，按 `NOTIFY_TASK` 选模板，
用正则从日志里抠指标。**日志就是接口**：采集器打印的 `课程总数：N` / `待完成：N` / `[urgent] …`
必须和 `TASK_TEMPLATES` 里的正则对得上，改一边就要改另一边。

**降噪闸门（用户硬要求「正常运行的不用给我汇报」）**：
`status === 'success' && urgent.length === 0` → **`process.exit(0)`，一条消息都不发**。
只有失败/取消，或日志里出现 `[urgent]` 才发卡片。

卡片颜色只有三种：成功 → 绿 `✅`；失败 → 红 `❌`；有 `[urgent]` → 橙 `⏰`（三时段卡片也用橙）。
`[urgent]` 行会置顶显示在卡片最上方。没配 `FS_WEBHOOK` 就静默 exit 0，不影响主流程。

**`[urgent]` 的定义收窄过两次**（`study_collector.urgent_alerts()`）：
只认 **24h 内截止且可做**的作业 —— 逾期任务做不了、且长期常驻（实测 2 条），
算进去会让闸门每轮都开、降噪失效。并且按**任务 ID 签名**跨轮去重：
签名存在 `data/study/meta.json` 的 `urgent_sig`，与上轮相同就打 `[urgent-same]` 且不告警。
**签名不含 deadline** —— 非精确截止是每轮重算的，带进去签名每小时都变。

## 6. 失败时会怎样

- **`tick`（cron 唯一入口）→ 单个采集器抛异常只记进 `runtime.errors[mode]`，其余照跑，最后仍渲染。**
  失败的采集器 `last_ok` 不前进，`last_try` 前进 → 按自己的间隔重试，不会每 20 分钟撞一次墙。
  `tick` 的返回值只看 `finalize`：渲染成功就算这一轮成功，README 不会被半成品冲掉。
- 单独跑 `study` / `diary` / `notice` / `schedule` → 异常被捕获、打摘要、返回 1 → **不渲染**（保留上一版 README）
- `all` 模式 → 逐个跑，单个失败不影响其他，最后仍渲染，只要渲染成功就返回 0
- 学习通登录失败 → 写 `meta.json{ok:false, reason:"login_failed"}`，README 顶部出 ⚠️ 告警，飞书报红
- 学习通登录成功但**一门课都没解析出来** → `ok:false, reason:"no_courses_parsed"`，
  绝不把「0 门课」当成「没有作业」写进数据（这是最危险的静默失败，见 [不足与风险](不足与风险.md) §1.2）
- AI 挂了 → 公告退回关键词打分，日记跳过 AI 通道但**复选框通道照常工作**；
  AI 失败的文件**不推进 sha**，下一轮自动重试
- 渲染挂了 → 返回 1，README 保持上一版
- 飞书挂了 → 只打日志，不影响 job 状态（通知是 `if: always()` 的附加步骤）

**异常摘要而不是完整栈**：`main.py` 里所有 `except` 都调 `utils.exc_brief(e)`，
它先脱敏、再只保留「异常类型 + 最后一行 + 最内层帧的文件名行号」，截断到 300 字符。
完整 traceback 会把局部变量里的 URL、请求头、cookie 一起带进**公开**日志。
`utils.py` 里唯一 `import traceback` 的地方就是 `exc_brief` 自己，用的是 `extract_tb`（只取帧位置，不取变量值）。

## 7. 日志与脱敏 —— 两道闸

仓库是**公开**的，Actions 日志任何人都能看。所以脱敏不是「顺手做一下」，是硬约束。

**第一道：Python 侧 `utils.log()`**，唯一的输出闸口。`_REDACT_PATTERNS` 覆盖：

| 类别 | 匹配形状 |
|---|---|
| 令牌 | `access_token=` / `Bearer xxx` / `sk-xxxxxxxx` / `ghp_xxxxxxxx` |
| 口令字段 | `password` / `passwd` / `pwd` / `api_key` / `apikey` / `token` / `secret` 后面的值 |
| **Cookie 字段** | `Cookie` / `Set-Cookie` / `JSESSIONID` / `_uid` / `UID` / `uf` / `_d` / `vc3` / `fid` / `unam` / `route` |

**不要绕过它直接 `print`** —— requests 的异常字符串里带着完整 URL 和 token。
`exc_brief()` 也走同一套 `_REDACT_PATTERNS`，所以异常摘要同样安全。

**第二道：JS 侧 `notify_feishu.js` 的 `redact()`**。
飞书卡片的内容来自 `NOTIFY_OUTPUT`（日志 tail）和命令行参数（AI 写的推送文案），
这两条路**都不经过 Python 的 `log()`**：AI 可能把用户日记里的隐私原样吐出来，
第三方库的 warning 可能直接写 stderr。所以 JS 侧用**同一套正则**再过一遍，
`payload` 里的纯文本和卡片正文都套 `redact()`。改一边必须改另一边。

**第三层是结构性的**（不靠正则）：

- `utils.scrub_task_title()` 去掉课程名里内嵌的同学学号（`张三2024 - 2025` 这种形状）
- `utils.public_url()` 把深链里的 `cpi` / `enc` / `_uid` 等个人参数删掉，只留课程/作业 ID
- `utils.strip_personal_fields()` 删掉 task 里的 `student_name` 等字段
- `render_readme.py` 往 `docs/data/` 拷 plans/quotes 时删掉 `source_file`（私有仓库的文件路径）
- `study_collector.diagnose()` 把所有数字打成 `D`、标题打成 `TITLE` —— 诊断输出必须能在公开日志里看
- `DIARY_EXCLUDE` Secret（逗号分隔的目录前缀）让日记采集**根本不读**那些目录，
  `drop_excluded()` 再清掉黑名单生效前已入库的条目

日志同时写 stdout（Actions 界面可见）和 `$TASK_LOG_PATH`（飞书从这里读摘要）。

**自检覆盖**：`selftest` 里有断言检查 `scrub_task_title` / `public_url` / `strip_personal_fields` /
`exc_brief` 的行为，以及 `notify_feishu.js` 的 `redact()` 是否真的被套在 payload 上。
