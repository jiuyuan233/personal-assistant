# 工作原理

一次运行从 cron 到飞书卡片发生了什么。技术选型的**理由**在 [技术路径.md](技术路径.md)，这里只讲**流程**。

## 0. 调度：一个 workflow，八条 cron

`.github/workflows/assistant.yml` 挂了 8 条 cron，靠 `github.event.schedule`（**cron 表达式原文**）判断该跑哪个模式：

| cron (UTC) | 北京时间 | 模式 | 联网 | 花 token | 提交文件 |
|---|---|---|---|---|---|
| `*/20 * * * *` | 每 20 分钟 | `finalize` | ❌ | ❌ | README + docs |
| `7 0,4,8,12 * * *` | 08:07 / 12:07 / 16:07 / 20:07 | `diary`（**只读采集**） | Gitee API | ✅ | 只 data |
| `7 16,18,20 * * *` | 00:07 / 02:07 / 04:07 | `diary`（**凌晨写回**） | Gitee API | ✅ | data + **用户日记仓库** |
| `13 * * * *` | 每小时 13 分 | `study` | 学习通 | ❌ | 只 data |
| `17 1,7,13 * * *` | 09:17 / 15:17 / 21:17 | `notice` | 学校公告站 | ✅ | 只 data |
| `2 23 * * *` | 07:02 | `morning` | 一言 + AI | ✅ | **不提交** |
| `2 4 * * *` | 12:02 | `noon` | 一言 + AI | ✅ | **不提交** |
| `2 14 * * *` | 22:02 | `night` | 一言 + AI | ✅ | **不提交** |

**为什么 diary 分成白天班和凌晨班**：用户白天在 Obsidian 里写日记，
白天往他的仓库提交会和他的编辑撞车。所以**白天只读**（采集名言/计划、复查勾选），
**只有凌晨班才写**。真正的守卫在代码里而不是 cron 里 ——
`diary_writeback.in_window()` 按 `data/sources.json` 的 `writeback_window`（默认 `00:00-05:00`，北京时间）判定，
窗口外直接返回 `skipped=outside_window`，一次提交都不发。
这样即使手动派发 `diary`、或者 Actions 延迟到白天才跑，也不会写进用户的日记。
凌晨排三次（00:07 / 02:07 / 04:07）是为了失败还有重试机会；内容无变化时不提交，多跑不产生额外 commit。

**为什么用 cron 原文而不是当前分钟数**：GitHub Actions 的 schedule 经常延迟 5–20 分钟，
高峰期甚至整点跳过。用 `date +%M` 判断会在延迟时全部落到 `finalize`，采集就永远不跑了。
匹配 cron 字符串则不受延迟影响。未知表达式一律兜底 `finalize`（最便宜、最安全）。

**为什么推送是分钟 2 而不是 0**：0 分会和 `*/20` 的 finalize 撞在同一时刻抢同一个 group。

`workflow_dispatch` 可手动指定 11 个模式，含 `all` / `probe` / `selftest` / `morning` / `noon` / `night`。

**concurrency 分两个 group**（表达式判断）：推送模式走 `pa-push`，其余走 `pa-collect`。
这样采集排队不会把定时推送挤掉。`cancel-in-progress: false` —— 宁可排队也不打断正在写数据的那次。

**⚠️ 但同一个 group 只保留一个 pending run。** 一次性派发多个模式，后派发的会把先派发的
**直接 cancel**（实测两条 CANCELLED）。**手动派发必须串行，等上一个 completed 再派下一个。**

## 1. 采集层（只有三个模式联网）

### study：学习通四步链

```
① POST passport2.huuc.edu.cn/fanyalogin
     uname / password 都要 AES-128-CBC 加密（key = iv = u2oh6Vu^HWe4_AES，PKCS7，base64）
     先 GET /login?fid=12 拿 cookie，再带 X-Requested-With: XMLHttpRequest
② GET  mooc2-ans.huuc.edu.cn/visit/courses/list      → 14 门课的 courseid/clazzid/cpi（实测去重后）
③ GET  mooc1.huuc.edu.cn/visit/stucoursemiddle       → 跟 302，从落地页抽 #enc / #workEnc / #examEnc
④ GET  /mooc2/work/list?courseId=&classId=&enc=<workEnc>          → 作业 + 互评
   GET  /exam-ans/mooc2/exam/exam-list?courseid=&clazzid=&enc=<examEnc> → 考试
```

③ 是**每门课都要重做一次**的：enc 是一次性令牌，不能跨课复用，也不能存起来下次用。
④ 两个接口参数大小写不同（作业 camelCase，考试全小写），搞混就返回「参数传递不正确！」。

解析出的每条任务算一个稳定 ID（`course_id|class_id|kind|work_id|answer_id` 的 md5，**不含 enc**），
截止时间 = 抓取时刻 + 页面倒计时（列表页不给绝对时间）。每门课之间 sleep 0.3s。

### diary：Gitee 增量

不 clone，走 API v5 `GET /repos/{repo}/contents/{path}`（中文路径必须百分号编码进 **URL 段**，不能用 `?path=`）。
递归列出 Tasks 下所有 `.md`，拿每个文件的 **git blob sha** 和 `data/diary/state.json` 里的比对：
sha 变了才处理，没变直接跳过。按文件名倒序（新的先处理），单次上限 `max_files_per_run`。

每个变更文件走**两条并行通道**：

- **确定性通道**：正则抓 Obsidian 复选框 `- [ ]` / `- [x]` → `origin: "checkbox"`，`confidence: 1.0`
- **AI 通道**：整篇喂模型 → 名言（逐字引用）+ 潜在计划（复选框里已有的**不许重复输出**）→ `origin: "ai"`

只有处理成功的文件才写回 state，失败的下次自动重试。

### notice：公开公告页

零登录。抓 `data/sources.json` 里 enabled 的站点，跟「下页」链接翻页（列表是**倒序**的，第一页最新）。
每条公告抽标题（优先 `title` 属性，教务处会截断可见文本）+ 发布日期 + 绝对 URL。

日期抽取有个坑：日期常在 `<a>` **外面**（前一个兄弟节点），所以要回看 200 字符；
而回看窗口可能命中**上一条**公告的日期，因此取「最靠近链接的那个匹配」（`m.end()` 最大），不是第一个匹配。

然后两道关：

1. **关键词门**：`block` 命中直接丢（放假/调课/党建…），`gate` 命中才进入候选，上限 30 条
2. **AI 打分**：每批 10 条，输出 0–5 分 + 分类 + 理由 + 截止日期。没配 key 或调用失败 → 退回纯关键词打分（boost=3 / gate=2）

### schedule：课表（离线）

读 `assets/WakeUp导入课表.ics`。WakeUp 的三个特点决定了处理方式：
每周一个 VEVENT、`RRULE:FREQ=WEEKLY;COUNT=1`（所以不用展开循环规则）、`DTSTART` **不带时区**（按北京时间解释）。

学期第一天不是配置项，是反推的：每条 event 算 `date - weekday天 - (week-1)*7天`，取众数 → `2026-09-07`。
节次靠一张 11 节的作息表精确匹配起止时间。

**`finalize` 每次都会重跑课表解析**，因为它是纯离线的、代价可忽略，而教学周必须每天前进。
否则 `current_week` 会停在最后一次手动跑 `schedule` 的那一周。

## 2. 合并层：两种相反的策略

`dedup.py` 是整个项目最容易改错的地方。核心判断：**这份数据的旧值和新值，哪个更可信？**

| | 公告 notices | 任务 tasks |
|---|---|---|
| 策略 | **旧值优先** | **新值优先** |
| 为什么 | AI 每天重打分，描述/评分会抖动；标题日期是客观事实，不该被覆盖 | 倒计时每小时都在变，旧值就是错值 |
| 例外 | `score` **只升不降**（避免好机会被误降后消失） | 旧记录有 `deadline_exact` 而新的没有 → **保留旧的精确值** |
| 清理 | 超过 120 天丢弃 | 不丢（已完成的进 README 折叠块） |

名言按**文本**去重（同一句话出现在多天日记里只留一条）；计划按 `text + source_file`。

计划的三条保护规则（优先级从高到低）：

1. 旧记录 `state == "cancelled"` → 直接跳过。**人工否决优先于一切**
2. 新记录 `origin == "checkbox"` → 无条件采用新 state。你在 Obsidian 里把 `[x]` 改回 `[ ]`，程序必须跟着改
3. 旧记录 `state == "done"` → AI 不能把它重新打开

## 3. 渲染层：零网络、零 token

`render_readme.py` 只读 `data/`，不 import 任何采集器，也不 import `ai_client`。这是结构上的保证。

1. `bucket_tasks` 把待完成任务分四桶：`overdue` / `today` / `week`(7天内) / `later`(更远**或无截止时间**)。
   四桶互斥，桶内按 deadline 升序，无 deadline 排最后。
2. 填 `readme_template.md` 的 `{{占位符}}` → 写 `README.md`。
   非精确截止时间前面加 `≈`；已提交/已完成的最近 20 项塞进 `<details>` 折叠块。
3. 顶部告警按优先级只出一个：🔴 有逾期 > 🟠 今天有截止 > ⚠️ 学习通未同步。
4. `week_svg.py` 手写 SVG 周课表（7 列 × 11 节，无图形库），今天的列高亮。
5. 把前端要用的数据裁剪进 `docs/data/*.json`（GitHub Pages 只能伺服 `docs/`）。

## 4. 提交

```bash
git add data docs README.md
git diff --cached --quiet && exit 0     # 没变化就不产生空提交
git pull --rebase origin <ref>
git push                                # 不带 --force
```

`probe` / `selftest` 模式跳过这一步（它们不该改数据）。
推不上去就让这步**失败**，飞书报红，人来处理——绝不用 force push 掩盖冲突。

## 5. 飞书通知（`if: always()`）—— 两条路

workflow 的飞书步骤先看 `/tmp/push-message.txt`：

```bash
if [ -s /tmp/push-message.txt ]; then
  node scripts/notify_feishu.js "$(cat /tmp/push-message.txt)"   # 纯文本：三时段人格消息
else
  node scripts/notify_feishu.js                                  # 卡片：运行状态
fi
```

**路 A：三时段推送（morning / noon / night）**
`daily_push.py` 拼事实 → 取一言 → AI 写文案（失败则确定性降级）→ 写进 `/tmp/push-message.txt`。
执行步骤开头有 `rm -f /tmp/push-message.txt` 清残留，**所以推送模式崩在写文案之前时，
会自动落到路 B 报红**，不会静默成功。

**路 B：运行状态卡片（采集 / finalize / selftest / probe）**
`notify_feishu.js` 读 `/tmp/task-output.log` 的最后 200 行，按 `NOTIFY_TASK` 选模板，
用正则从日志里抠指标。**日志就是接口**：采集器打印的 `课程总数：N` / `待完成：N` / `[urgent] …`
必须和 `TASK_TEMPLATES` 里的正则对得上，改一边就要改另一边。

卡片颜色：失败 → 红；有逾期 → 洋红 `⚠️`；有 24h 内截止 → 橙 `⏰`；否则绿。
`[urgent]` 行会置顶显示在卡片最上方。没配 `FS_WEBHOOK` 就静默 exit 0，不影响主流程。

## 6. 失败时会怎样

- 单个采集器抛异常 → `main.py` 捕获、打 traceback、返回 1 → **不渲染**（保留上一版 README，不会把好数据冲掉）
- `all` 模式 → 逐个跑，单个失败不影响其他，最后仍渲染，只要渲染成功就返回 0
- 学习通登录失败 → 写 `meta.json{ok:false, reason:"login_failed"}`，README 顶部出 ⚠️ 告警，飞书报红
- AI 挂了 → 公告退回关键词打分，日记跳过 AI 通道但**复选框通道照常工作**
- 渲染挂了 → 返回 1，README 保持上一版

## 7. 日志与脱敏

所有输出走 `utils.log()`，它是唯一的脱敏闸口：`access_token=` / `Bearer` / `sk-` / `ghp_` /
`password=` 之类一律替换成 `***`。**不要绕过它直接 print**——requests 的异常字符串里带着完整 URL 和 token。

日志同时写 stdout（Actions 界面可见）和 `$TASK_LOG_PATH`（飞书从这里读摘要）。
