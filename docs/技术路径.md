# 技术路径

本文记录**每个技术选型的理由、被否决的方案、以及实测证据**。
目的是让接手的人不用重新踩一遍坑。

---

## 0. 总体架构

```
GitHub Actions (cron)
        │
        ├─ finalize  每20分钟 ──→ 读 data/*.json + 离线重算课表 ──→ README.md + docs/week.svg + docs/data/*
        ├─ diary     每天4次  ──→ Gitee API v5 ────→ AI 抽取 ──→ data/diary/*
        ├─ study     每小时   ──→ 学习通四步链 ───→ 纯解析 ──→ data/study/*
        └─ notice    每天3次  ──→ 公开公告列表 ───→ AI 评分 ──→ data/notice/*
                                                          │
                                                          └─→ git commit + push
                                                          └─→ 飞书卡片（if: always()）
```

**核心设计：采集层与渲染层彻底分离。**

- 采集层写 `data/`，各自独立频率，失败互不影响
- 渲染层只读 `data/`，**零网络、零 token**，所以能每 20 分钟跑一次
- 任何一个源挂了，README 照样渲染，只是那块数据旧一点，并在「数据源状态」里标红

这是从 `wool-gathering` 学来的最有价值的一点。

## 1. 为什么用 GitHub Actions 而不是服务器

| 方案 | 结论 |
| --- | --- |
| **GitHub Actions** ✅ | 免费、无需运维、自带 cron 和日志、结果直接 commit 进仓库 |
| 国内云服务器 | 要钱、要运维、要备案，个人项目不值当 |
| 青龙面板 | 适合签到类，但 README 渲染和 Git 提交要自己搭 |
| 本地常开电脑 | 不可靠，断电断网就停 |

**Actions 的三个已知约束及应对：**

1. **cron 最小粒度 5 分钟，且不保证准时**（高峰可能延迟十几分钟）
   → 模式判定用 `github.event.schedule`（cron 表达式原文）而不是当前分钟，
     这样延迟触发也不会跑错模式。
2. **60 天无 push 自动停用 schedule**
   → 本项目每小时都有数据变更，正常不会触发。
3. **私有仓库 2000 分钟/月免费额度 —— 这是硬约束，不是可以靠优化绕过的**
   Actions 按「每个 job 向上取整到分钟」计费，一次 finalize 跑 30 秒也计 1 分钟。
   每 20 分钟一次 = 2160 次/月 = **至少 2160 分钟，单这一项就超了 2000**。
   加上 study（720 次 × 约 3 分钟 ≈ 2160）、diary、notice，默认配置约 4700 分钟/月。

   → 结论：**默认配置要求 public 仓库（无限额度）或 self-hosted runner（无限额度）**。
     self-hosted 放国内机器还顺带解决了第 5 节的海外 IP 风险，是一举两得的选择。
   → 必须 private + GitHub 托管的话，只能放宽节奏。`DEV_GUIDE.md` 第 2 节给了现成的
     省额度 cron 组合（finalize 每 2 小时 / study 每 3 小时），预算约 1500 分钟/月。
     代价可控：**每个采集模式跑完都会自动渲染**，所以 study 的频率实际上就是 README 的刷新频率，
     finalize 只补中间空档。
   → 已做的优化：diary 从每小时 3 次降到每天 4 次（日记一天最多改一次，72 次/天纯属浪费），
     省掉约 2000 分钟/月。

## 2. 源1：Gitee 日记

### 选型：Gitee API v5，不用 git clone

**实测证据：**

- `git clone --depth=1` 整个仓库 → `fatal: fetch-pack: invalid index-pack output`
  原因：仓库里有二进制附件（图片等），浅克隆打包失败。
- `git clone --depth=1 --filter=blob:none --no-checkout` + `sparse-checkout set --no-cone "总仓库个人-Sync/个人信息/个人信息/Tasks"`
  → 成功，397 KB。但每 20 分钟 clone 一次仍然偏重。
- **API v5 contents 接口** → 成功，目录列表 4 KB，单文件 1.3 KB。✅ 最终方案

### 两个 API 坑（都实测踩过）

1. **中文路径必须编码进 URL 路径段**
   ```
   ❌ /contents/Tasks?path=总仓库个人-Sync/...     → 返回 []
   ✅ /contents/%E6%80%BB%E4%BB%93%E5%BA%93.../Tasks → 正常
   ```
   代码里用 `urllib.parse.quote(path, safe="/")`。

2. **目录列表不含 `content` 字段**，只有元数据 + git blob `sha`。
   要正文必须再请求单个文件（返回 base64）。

### 增量判定：用 blob sha，不用 git 历史

列表接口自带每个文件的 `sha`。`data/diary/state.json` 记录上次处理时的 sha，
只有 sha 变了才重新送 AI。

**为什么不用 `git diff`：** 需要足够的克隆深度，`--depth=1` 下拿不到历史；
而 sha 比对不需要任何历史，且天然幂等。

### 实际目录结构（实测）

```
Tasks/
  <私人目录>/     (dir)
  年/           (dir)
  日/           2026-09-28.md … 2026-10-15.md  ← 日记主体，15 个文件
  月/           10月.md、11月.md
  <私人目录>/       个人方案/、资料搜索/  (dir)
```

递归深度上限 3 层，只取 `.md`。

### 计划抽取：双通道

- **复选框 `- [ ]` / `- [x]` 由程序确定性解析**，置信度 1.0，状态权威。
  实测日记里就有 `- [ ] 宋浩数学cot章节` 这种，正则比 AI 可靠得多。
- **AI 只挖隐含意图**（「一直想学…」「该把…捡起来了」），
  提示词里明确禁止重复输出复选框内容，避免重复和 token 浪费。

`dedup.merge_plans()` 保护人工标记：`cancelled` 永不被覆盖；
复选框来源的更新可以覆盖 `done`（作者把 `[x]` 改回 `[ ]` 要跟着变）。

## 3. 源2：学习通（ hardest 的部分）

> 📎 本节的接口结构来自开发期对用户抓包的实测（学习通 67 条请求、空间页 4 条请求）。
> **抓包文件本身已永久移除并抹除 git 历史** —— 脱敏不彻底，复合参数只遮了一半，
> 班级 ID 等标识仍是明文，足以定位到用户。原因与教训见 [原始文件.md](原始文件.md)。
> 所以这里只保留**文字化的结构结论**：方法、路径、参数名、状态码、时序特征。
> 需要复看一手证据时，在本地重新抓包，看完即删，**不要提交**。

### 选型：纯 HTTP 模拟登录，不用浏览器自动化

| 方案 | 结论 |
| --- | --- |
| **requests + AES 手工加密** ✅ | 快（全程 <2 分钟）、依赖少、Actions 上稳定 |
| Playwright/Selenium | 要装浏览器（~300 MB）、慢、Actions 上易超时；**已从 requirements 移除** |
| 现成开源库（如 chaoxing-toolkit） | 多为签到/刷课设计，且普遍硬编码公有云域名，不适配学校私有化部署 |

### 学校是私有化部署，不是公有云

域名全是 `*.huuc.edu.cn`，`fid=12`。任何写死 `chaoxing.com` 的库都不能直接用。

### 四步链（实测打通，含失败路径）

```

2  GET  mooc2-ans.huuc.edu.cn/visit/courses/list?v=1&rss=1&start=0&size=100
   → 28 个 stucoursemiddle?courseid=&clazzid=&cpi=577967959&ismooc2=1

3  GET  mooc1.huuc.edu.cn/visit/stucoursemiddle?...（跟随 302）
   → 302 到 mooc2-ans.huuc.edu.cn/mooc2-ans/mycourse/stu?...&enc=<新铸>&t=<时间戳>

**AES 参数（实测确认）：**
```

```
key 和 iv 是同一个值，这是超星的固定实现。

### 踩过的五个坑（每个都实测复现过）

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 「无权限的操作！」（试了 5 次） | 缺 `ut=s`，且缺 `stuenc` | 两个都带上 |
| stu 页返回 791 B 提示页 | `t` 查询参数必须是配对值 | 别自己拼 URL，**跟随 302** |
| `studentcourse` 里的 `var enc` 用不了 | 那是 `oldenc`，不是 stu 的 `enc` | 只认 stu 页的隐藏字段 |
| 考试列表「参数传递不正确！」 | **考试模块用小写 `courseid/clazzid`** | 作业驼峰、考试小写，分开写 |
| `stu-job-info` 返回「班级id为空」 | 参数不是 courseid/clazzid/cpi | 正确参数是 `clazzPersonStr`（`clazzid_cpi` 逗号拼接）。本项目未使用该接口 |

**考试列表的解法是实测出来的**：试了三种参数组合，
`courseid=&clazzid=&cpi=&ut=s&stuenc=&enc=` → 35788 B，`<title>考试列表</title>` ✅
另两种（驼峰、或 `examEnc=` 作参数名）都返回 1166 B 的「参数传递不正确！」。

首次真实 `study` 跑完，14 门课的名字**全是「在线学习诚信承诺书」**。
根因：`stucoursemiddle` 落地页的首个 `<h2>` 是全站横幅，不是课程名。

实测正确的两个来源（已用真实 HTML 验证 14/14 命中）：

```html
<!-- 1) 课程列表页 /visit/courses/list，每个 li 内 -->
<span class="course-name overHidden2" title="大学生职业生涯与发展规划">大学生职业生涯与发展规划</span>

`course-name` span 的 `title`；`mint()` 仅在名字仍为空时用 `<title>` 兜底
（`<title>提示</title>` 是错误页，要排除）。

真实课程名样本：大学生职业生涯与发展规划、国家安全教育、2026级-校规校纪、

> `201780805` 在列表里出现两次是**正常的**：两个不同 `clazzid`，按 `(courseid, clazzid)` 去重后仍是两条。

### 状态词表必须包含「未交」（2026-11-13 实测纠正）

真实作业列表用的待交状态词是 **`未交`**，而词表里只有 `未提交`/`待提交`，
`DONE` 里倒是有 `已交`。结果 3 条真待交作业被判 `unknown` 漏出任务清单，
其中两条带真实截止时间（2026-11-19、2026-11-20）。已把 `未交` 补进 `PENDING`，
并加自检断言锁住。**日后再遇到 unknown 状态，先 dump 原文再补词表，不要猜。**

考试行结构不同：
```html
<li><div onclick="viewExamAnswer('10959519','170844300')">
  <div class="right-content"><p class="overHidden2 fl">第二章测试题</p>
  <p class="status fl">已完成</p></div></div></li>
```

### 截止时间：只能推算

**列表页没有任何绝对时间戳**，只有相对倒计时。所以：

```
deadline = 抓取时刻 + parse_remaining("剩余1小时12分钟")
deadline_exact = False        # README 里显示 ≈
```

对「待完成且无倒计时」的任务，额外抓详情页补精确时间（每次最多 8 个，可配置）。
`dedup.merge_tasks()` 里**旧的精确值优先于新的估算值**，避免精度倒退。

### 状态语义的一个反直觉点

`待批阅` 通常是"已提交等老师批"，不该出现在待办里。
**但互评模式下**，实测样本第一行是 `label=互评` + `status=待批阅` + `剩余1小时12分钟`，
且没有对应的 eval-list 行 —— 这说明用户还得去互评。

所以 `parse_work_rows()` 有一条升级规则：
`submitted` + `label==互评` + 有倒计时 + 未过期 → `pending`。

### ID 设计

```python
make_id(course_id, class_id, kind, work_id, answer_id)
```
**绝不包含 `enc`** —— 它每次访问都变，进 ID 会导致每次抓取全部任务都变成"新任务"。

## 4. 源3：校园公告

### 选型：放弃 CAS 登录，改抓公开页

**原方案**：`icas.huuc.edu.cn/cas/login` → `portal.huuc.edu.cn`。

**实测否决理由：**
- POST 登录返回 **HTTP 500**，`execution` 为空
- 登录表单**完全由 JS 构建**（`name=" + encodeURIComponent(username)+"`）
- 还有 `captcha`、`mfaState`、`qrCodeKey` 字段
- 纯 HTTP 无法自动化；上 Playwright 又重又脆

**用户已确认同意改用公开页方案**：零登录、零封号风险，且比赛信息九成本来就公开发布。

### 实测可用的源

| URL | HTTP | 大小 | 内容 | 启用 |
| --- | --- | --- | --- | --- |
| `www.huuc.edu.cn/index/tzgg.htm` | 200 | 52952 | 校网通知公告（数学竞赛、职业规划大赛校赛） | ✅ |
| `jwc.huuc.edu.cn/index.htm` | 200 | 28161 | 教务处（大创计划立项） | ✅ |
| `jwc.huuc.edu.cn/AIfnjyjx/hdtz.htm` | 200 | 23824 | 教务处活动通知 | ✅ |
| `tw.huuc.edu.cn/tzgg.htm` | 200 | 13920 | 校团委通知公告 | ✅ |
| `hncj.goworkla.cn` | 200 | 96874 | 招生就业处（第三方建站，结构不同） | ⬜ 默认关闭 |
| `cjrh.huuc.edu.cn` | — | — | **域名不存在**（早期猜测，已否决） | ❌ |

> 注：早期探测曾以为 `tw.huuc.edu.cn/tzgg.htm` 不存在，复测为 **200**，已启用。

### 三个站三种列表结构，一套解析规则

```html
www:  <a href="../info/1061/27179.htm" title="…"><div class="date"><b>09</b><span>2026-11</span></div><p>…</p></a>
jwc:  <li><span>10-28</span><a href="info/1018/5561.htm" title="…">…</a></li>
tw:   <li><a href="info/1007/10986.htm" title="…"><span>2026-11-06</span>…</a></li>
```

统一策略：
1. 正则抓所有 `href` 匹配 `info/\d+/\d+\.htm` 的 `<a>`
2. 标题优先取 `title` 属性（jwc 的可见文本被截断成 `…`，title 才是全的）
3. 日期**先在 `<a>…</a>` 内部找**，找不到再往前找 200 字符
4. `urljoin` 把相对链接转绝对

**往前找日期时必须取「离锚点最近」的匹配**，不能按模式优先级取第一个 ——
否则 200 字符窗口里会混进上一条公告的日期。这个 bug 在写自检用例时发现并修掉了
（`notice_collector._match_date(nearest=True)`）。

### 分页是倒序的

```html
<span class="p_no"><a href="tzgg/220.htm">2</a></span>   ← 第2页
<span class="p_no"><a href="tzgg/1.htm">221</a></span>   ← 第221页（最旧）
<span class="p_next"><a href="tzgg/220.htm">下页</a></span>
```

`tzgg.htm` 是最新一页，页码越大越旧。**跟着「下页」链接走，不要自己算页码**
（总页数会变）。每源默认抓 1–2 页。

### 相关度：关键词门控 + AI 评分

- 关键词命中才送 AI（`keywords.gate`），未命中的仍入库但 `score=0`，**不花 token**
- `keywords.block` 直接排除（放假/调课/值班/党建）
- AI 按 0–5 打分，提示词里写死了用户画像（建环专业 + AI/Agent 兴趣）
- 每批 10 条，每次最多 30 条候选
- **AI 失败时退回关键词打分**，不会让整个源挂掉
- `merge_notices()` 里**相关度只升不降**，避免模型每天抖动导致 README 无意义 diff

## 5. 课表

### WakeUp .ics 的三个特点（实测 186 条 VEVENT）

1. **每周一条 VEVENT**，`RRULE` 全是 `FREQ=WEEKLY;COUNT=1` → **不需要展开循环规则**
2. **DTSTART/DTEND 不带时区**（floating time）→ 必须按 Asia/Shanghai 解释
3. `DESCRIPTION` 是「第N周」，这是唯一的周次来源

### 学期起点反推

用 `事件日期 - 星期偏移 - (N-1)×7天` 反推第1周周一，**取众数**（个别周次写错也不影响）。

实测验证：`20261007` 是周三、`第5周` → 第5周周一 = 10-05 → 第1周周一 = **2026-09-07**。
日期范围 2026-09-14 ~ 2027-01-08，共 12+ 周。

### 节次映射

实测所有起止时间都能精确对上一张作息表：

| 节次 | 起 | 止 |
| --- | --- | --- |
| 1 | 08:00 | 08:45 |
| 2 | 08:50 | 09:35 |
| 3 | 10:05 | 10:50 |
| 4 | 10:55 | 11:40 |
| 5 | 14:00 | 14:45 |
| 6 | 14:50 | 15:35 |
| 7 | 16:05 | 16:50 |
| 8 | 16:55 | 17:40 |
| 9 | 19:00 | 19:45 |
| 10 | 19:50 | 20:35 |

## 6. AI 层

### 选型：OpenAI 兼容协议 + 通用中转站

`ai_client.py` 直接复用 `wool-gathering` 的实现（未改动），因为它是协议无关的：
`AI_BASE_URL` / `AI_API_KEY` / `AI_MODEL` 三个环境变量就能换任意中转站。

**已内置的保护：**
- 滑动窗口限流 `RateLimiter(45次/300秒)`
- 429 指数退避重试 3 次
- `chat_json()` 注入严格 JSON system 提示 + 三级容错抽取
  （裸 JSON → ```json 代码块 → 首个 `{` 到末个 `}`）

### 为什么不用 function calling

部分中转站不支持 `tools`。让模型直接输出 JSON 文本再抽取，兼容性最好。

### max_tokens 的坑

推理型模型（如 deepseek-r1）会把 token 预算花在思维链上，
`max_tokens` 太小会导致 `content` 为空。默认 2000 是安全值，别调小。

### 截止日为什么不能只靠提示词（2026-11-13 实测）

`ai_detail()` 第一版无条件采纳模型返回的 `deadline`，拿到三个日期，看着像成功。
逐条抓正文复核后，**只有一个成立**：

| 模型给的截止日 | 正文实际情况 | 结论 |
| --- | --- | --- |
| `2026-10-30` | 原话是「学院初赛阶段：10月1日—10月30日」，全文没有「截止」二字 | 赛程阶段结束日，误判 |
| `2026-09-18` | 正文里**根本不存在**这个日期（各种写法都搜不到） | 模型编造 |
| `2026-05-31` | 原话「2026年5月31日报名截止」 | 成立，保留 |

先按常规做法收紧 `DETAIL_INSTRUCTIONS`，明确排除赛程阶段日、发文日、举办日，
清空这三条的 `description` + `deadline` 重抽 —— **摘要变好了，三个截止日一字未变**。
结论：提示词能改善摘要质量，但拦不住日期幻觉，**必须有代码级硬校验**。

于是加 `deadline_supported(text, dl)`，两个条件同时满足才采纳：

1. 正文出现报名截止语义：`DEADLINE_CUE_RE` = `截止|逾期|不予受理|前报送|之前报送|报名[^。；]{0,12}前|提交[^。；]{0,12}前`
2. 该日期能在正文里找到，兼容 `2026-05-31` / `2026年5月31日` / `5月31日` / `2026.5.31` / `5.31` / `5-31`

不满足就丢弃并打 WARN（`截止日 X 在正文里没有报名截止依据，丢弃：<url>`），
真实 runner 上已验证拦掉 `2026-10-30`。selftest 加 2 条断言，总数 32 → **34**。

⚠️ 两个交接注意点：
- `ai_detail()` 只在 `deadline` 为空时写值（公告是旧值优先合并），**存量错值不会被自动纠正**，
  要手工清 `data/notice/notices.json` 里对应字段。
- 校验依赖 `body_text()` 取到完整正文。容器取错（见下）会让日期搜不到，表现为「全部丢弃」，
  别误判成校验太严。

### 正文容器必须按 div 深度闭合

博达 CMS 正文在 `<div class="v_news_content">`。第一版从容器名出现位置起取固定 30000 字符，
结果把页脚、「上一篇/下一篇」导航一起喂给 AI，既浪费 token 又污染摘要。
改成从容器开标签之后开始数 `div` 嵌套深度，遇到匹配的闭合标签就停。
真实页面正文 2756 → 2387 字符。selftest 有 2 条断言守着（取到容器内容 / 不含导航页脚）。

### 模型名必须照抄 `/models` 目录（2026-11-13 实测）

首次真实 `diary` 跑完，**每次 AI 调用都 403**，12 个文件全部抽取失败。
第一反应容易误判成「key 失效」或「海外 IP 被封」，**两个都不是**：

```
GET  /v1/models                     → 200，31 个模型（key 完全有效）
POST /v1/chat/completions
     model=deepseek-v3-2            → 403「免费API仅可使用免费模型目录中的模型」
     model=deepseek-v3.2            → 200，content 正常
     model=gpt-4o-mini              → 200，content 正常
```

根因只是**模型名写错一个字符**：目录里是 `deepseek-v3.2`（点号），
配置里写成了 `deepseek-v3-2`（连字符）。免费档只允许目录内的模型，
所以报 403 而不是 404，极具误导性。

**排查顺序固定为：先 `GET /v1/models` 看目录，再逐个试模型名，最后才怀疑 key 或 IP。**
换中转站/换模型时，`AI_MODEL` 必须从该站 `/models` 的返回里复制，不要凭记忆写。

## 11. 一次真实的数据丢失事故（2026-11-13，已修）

**现象**：`study` 成功推送后，紧接着的 `diary` 抽出 24 条计划，却在提交步骤挂掉：

```
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
hint: You can instead skip this commit: run "git rebase --skip".
```

run 判定 failure，**24 条计划从未进仓库，直接丢了**。

**两个叠加的根因：**

1. `actions/checkout` 默认检出 `github.sha` —— **派发那一刻的 HEAD**。
   `diary` 派发时 HEAD 还是 `e243771`，排队期间 `study` 推了 `2ed980a`。
   于是 `diary` 在旧树上渲染 README（任务数 0），与远端新 README 必然冲突。
2. **每个模式都提交派生产物**。`main.py` 里采集模式跑完会顺手 `do_finalize()`，
   提交步骤又对所有模式 `git add data docs README.md`。
   两个模式各自渲染同一份 README，冲突面被人为放大到最大。

**修法（两条都要，缺一不可）：**

```yaml
# 1) 检出分支尖端，而不是派发时的 SHA
- uses: actions/checkout@v4
  with:
    fetch-depth: 0
    ref: ${{ github.ref_name }}

# 2) 采集模式只提交 data，派生产物统一交给 finalize
case "$MODE" in
  finalize|all) git add data docs README.md ;;
  *)            git add data; git checkout -- README.md docs ;;
esac
```

修完后冲突面只剩「同一模式自己写的数据文件」，而各采集模式写的是不同子目录
（`data/study`、`data/diary`、`data/notice`），实际上不可能再撞。
README 最多晚 20 分钟由 `finalize` 刷新，这个代价远小于丢数据。

**教训：采集层只写自己的数据，渲染层独占派生产物的提交权。**
这条边界一旦模糊，并发排队就会变成数据丢失。

## 12. 本轮改造的技术决策（2026-11-13）

### 12.1 三时段推送：为什么事实拼装不用 AI

用户要的是「有人格的每日陪伴」，但**人格可以交给 AI，事实不行**。
所以拆成两层：`diary_facts()` 确定性拼事实 → AI 只负责措辞。

被否决的方案：把 `plans.json` 整个丢给 AI 让它自己挑。
理由是模型会编造任务、把逾期说成今天、甚至拿课表来填 —— 而用户明确说课表不用它管。
现在事实集里**根本没有课表数据**，提示词再怎么写也编不出上课时间。

降级路径同理：`fallback_message()` 是纯模板，但仍带真实事实和一言。
判断 AI 是否成功用显式 `ai_ok` 布尔，**不用 `text.startswith(...)`** ——
后者在 AI 恰好以同样开头输出时会误判成降级。

### 12.2 推送 cron 为什么错开到分钟 2

`*/20` 的 finalize 落在 0/20/40 分。推送若也放 0 分，两者同一时刻抢同一个 concurrency group。
错开 2 分钟即可。另外给推送单独一个 group（`pa-push`），
这样采集排队不会把定时推送挤掉 —— 推送是用户直接感知的，优先级更高。

**但同 group 只保留一个 pending run**：`cancel-in-progress: false` 只保证不打断**正在跑**的，
不保证排队的不被顶掉。实测一次派发三个模式，两个直接 CANCELLED。
所以手动派发必须串行。这条写进了 AGENT.md 和本文档，因为它反直觉。

### 12.3 日记写回：为什么用 HTML 注释标记而不是追加 Markdown

被否决的方案一：直接往日记末尾追加待办。
问题是**无法区分哪些是助手写的、哪些是用户写的**，复查时会把用户自己的复选框当成助手任务，
而且重复运行会无限追加。

被否决的方案二：单独建一个 `助手待办.md`。
问题是用户要求「写到我今天的日记里面」，分文件就不满足需求，也不会在 Obsidian 日视图里出现。

采用的方案：`<!-- assistant:plans:start -->` / `<!-- assistant:plans:end -->` 包住区块，
每行带 `<!-- pid:xxx -->`。好处是：

- 区块外用户正文**一个字节都不碰**，`upsert_block()` 只替换 marker 之间的 span
- Markdown 渲染时注释不可见，Obsidian 里看着就是普通复选框
- 复查靠 **pid 对齐而非文本匹配**，用户改了字也认得出来
- 同日重复写回幂等，`[x]` 状态优先保住

**代价**：采集侧必须 `strip_assistant_block()` 后再抽取，
否则助手自己写的计划会被当成用户新写的再抽一遍 → 无限自我复制。selftest 有断言守着。

### 12.4 Gitee 写入：HTTP 200 + `{}` 的存在性陷阱

实测：**Gitee API v5 对不存在/已删除的文件返回 HTTP 200 和空对象 `{}`，不是 404。**
所以 `read_file()` 判断存在与否必须看 body 里有没有 `sha`。
只看状态码会把「文件不存在」误判成「文件存在但内容为空」，
接着不带 sha 去 PUT 更新就会被拒（Gitee 要求更新必须带当前 sha）。

新建走 POST，更新走 PUT + sha。写回失败只 WARN 不影响采集 —— 数据已落盘。

**sha 被拒会自动重试一次**：重读最新正文 → 重新 `upsert_block()` → 再提交。
被拒意味着用户或 Obsidian 同步刚好改过这个文件，重试时区块外以他的最新内容为准，
所以他凌晨临时补的一句话不会被覆盖。只重试一次，不无限循环。

**为什么写回只能在凌晨（用户硬要求）**：他白天在 Obsidian 里编辑日记，
白天提交会和他的编辑撞车。被否决的方案：只把 cron 挪到凌晨。
问题是**手动派发 `diary`/`all`、以及 Actions 延迟到白天才跑，都绕过了 cron**，照样会写。
采用的方案：守卫放进代码 —— `in_window()` 按 `sources.json` 的 `writeback_window`
（默认 `00:00-05:00`，北京时间，含头不含尾，支持跨零点）判定，
窗口外**只复查勾选、零提交**，返回 `skipped=outside_window` 且**不推进 `last_date`**，
滚动链条留到下一个凌晨窗口继续。配置格式写错时**失败关闭**（当天不写 + ERROR），
宁可漏一天也不能在用户编辑时提交。cron 侧再加凌晨班 `7 16,18,20 * * *`
（北京 00:07 / 02:07 / 04:07）提供三次机会，白天班降级为只读采集。

### 12.5 课表时间线：为什么是两层而不是一层

用户要「像日历那样的当前时间线」。SVG 是静态文件，只能由 finalize 每 20 分钟重画，
**20 分钟精度对「现在几点」来说太粗**。所以加了第二层：
`week_svg.py` 导出几何参数到 `schedule_geo.json`，网页 JS 每 30 秒按浏览器时间实时移动一条覆盖线。

被否决的方案：把 SVG 改成内联 `<svg>` 由 JS 直接操作。
理由是 README 里也要显示课表（`<img>` 引用），内联会让两处不一致，且手写 SVG 生成器要重写。

**几何算法的关键取舍**：每节课 45 分钟正好占满一行，课间线**停在两行交界不拉伸**。
如果按真实时间线性映射，大课间（08:50→10:05 有 75 分钟）会让线慢慢爬过下一行的上半部分，
看着像还在上课。现在用锚点分段插值：上课时段内线性，课间直接跳到下一行起点。
Python `time_y()` 和 JS `nowLineY()` 必须是同一套算法，改一边就要改另一边。

### 12.6 作业发布时间：实测取不到，诚实退回 first_seen

用户要求「开始时间到今天超过一周的任务就除去」。理想是用真实发布时间，但实测：
`work/task` 详情页 HTML 里只有空标签 `作答时间:`，**值由 JS 注入，静态 HTML 拿不到**。

被否决的方案：上 headless 浏览器渲染。理由是 Actions 上装 Playwright 既慢又脆，
且每小时跑一次，代价远大于收益。

采用：普通作业的 `start_time` 退回 `first_seen`（本助手首次发现时间），
**并在文档里明确写出这不是真实发布时间**。
只有互评任务能拿到真实窗口 —— `eval-list` 详情页有 `互评时间：11-06 07:01 至 11-10 23:01`（不带年份）。

这个诚实标注很重要：后续 AI 若看到「一周窗口」以为用的是发布时间，会做出错误推断。

### 12.7 课程身份：course_id 不够，必须加 class_id

实测英语课 `course_id=201780805` 在课程列表里出现**两次**，
`class_id` 分别是 156400069 和 156290484 —— 同一门课挂在两个教学班下。
原先 `course_rows()` 只按 `course_id` 归组，结果 README 里两行都显示同样 2 条任务
（一行作业数 3、另一行 0，自相矛盾）。

修法：`course_key(d) = (course_id, class_id)` 复合键，任务和课程两侧都用它。
**14 行本身是对的**（用户确实选了 14 个教学班），错的是任务归属。
