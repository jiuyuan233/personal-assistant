# 数据结构

所有列表文件的统一外壳（由 `dedup.save_list` 写出）：

```json
{
  "updated_at": "2026-11-12T23:40:00+08:00",
  "count": 42,
  "...": "调用方传入的额外 meta",
  "items": [ ... ]
}
```

`dedup.load_list` 两种都吃：直接是数组，或带 `items` / `tasks` / `notices` / `quotes` / `plans` 键的对象。
时间一律 **ISO 8601 带 +08:00**；只有日期的是 `YYYY-MM-DD`；空值用 `null` 不用 `""`。

## data/study/tasks.json

一条 = 一个作业 / 互评 / 考试。`extra meta: course_count`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `make_id(course_id, class_id, kind, work_id, answer_id)`。**绝不含 enc**，enc 每次刷新都变，含进去就会每次产生"新任务" |
| `kind` | str | `work` / `eval` / `exam`。同一份作业在列表里出现两次（`work/task` 和 `work/eval-list`），靠 kind 区分 |
| `course` | str | 课程名，来自**课程列表页 `course-name` span 的 `title`**，middle 页 `<title>` 兜底。**不是 middle 页 `<h2>`**——那是全站横幅「在线学习诚信承诺书」 |
| `course_id` `class_id` `cpi` | str | 超星三件套。**课程身份 = `course_id` + `class_id`**，同一门课可能挂两个教学班 |
| `title` | str | 任务标题 |
| `work_id` `answer_id` | str | 从 `onclick` 跳转 URL 的 query 里取 |
| `label` | str | 行内标签，如 `互评` / `作业` / `考试` |
| `status` | str | 页面原文，如 `待批阅` / `待互评` / `已完成` |
| `state` | str | 归一化：`pending` / `submitted` / `done` / `unknown` |
| `deadline` | str\|null | ISO 时间。**多数是推算值** |
| `deadline_exact` | bool | `true` = 详情页拿到绝对时间；`false` = 抓取时刻 + 剩余倒计时 |
| `remaining_text` | str | 页面原文 `剩余1小时12分钟`，留作人工核对 |
| `start_time` | str\|null | 开始时间。**普通作业拿不到真实发布时间**（详情页只有空标签 `作答时间:`，值由 JS 填），只能退回 `first_seen`；**只有互评任务**能从 `互评时间：11-06 07:01 至 11-10 23:01` 拿到真实窗口 |
| `url` | str | 任务直达链接（含临时 enc，会过期，只作参考） |
| `first_seen` `last_seen` | str | 首次/最近一次出现的日期 |

**state 语义**（`study_collector.classify`）：

- `pending`：待做 / 未做 / 待提交 / 未提交 / 待完成 / 进行中 / 待互评 / 待考试 / 未开始 / 待作答 / 待批阅互评
- `submitted`：待批阅 / 已提交 / 批阅中 / 待批改 / 批改中
- `done`：已完成 / 已互评 / 已批阅 / 已结束 / 已交 / 已评分
- **例外**：`submitted` + `label == "互评"` + 仍在倒计时 → 提升为 `pending`。互评模式下"待批阅"意味着你还得去评别人，不是没事可做。

**deadline 推算**：列表页只给相对倒计时，所以 `deadline = 抓取时刻 + parse_remaining(remaining_text)`。
误差 = 抓取到解析的延迟（秒级）+ 页面倒计时的取整（分钟级）。渲染时非精确值前面加 `≈`。
合并时若旧记录有 `deadline_exact` 而新记录没有，**保留旧的精确值**。

## data/study/courses.json

`items[]`：`course_id` `class_id` `cpi` `name` `task_count` `pending_count`。

## data/study/meta.json

不是列表，是单个对象：

```json
{"last_attempt":"...","last_success":"...","ok":true,"status":"ok",
 "courses":28,"courses_ok":27,"courses_failed":1,"tasks":180,"pending":3,
 "unknown_deadline":0,"anomalies":[],
 "urgent_sig":"<任务ID>,<任务ID>","urgent_count":2}
```

| 字段 | 说明 |
|---|---|
| `status` | `ok` / `partial` / `failed`。**`ok:true` 不等于 `status:"ok"`** —— 有失败课程、可疑清空、课程数偏离、截止未知都会降级成 `partial` |
| `anomalies` | 最多 12 条异常描述，飞书红卡与 README 告警都读它 |
| `urgent_sig` | 本轮 **24h 内截止且可做**的任务 ID 排序后逗号拼接。**只含 ID，不含 deadline** —— 非精确截止是「抓取时刻 + 列表页倒计时」每轮重算的，带进去签名每小时都变、去重就废了 |
| `urgent_count` | 上述条数。与上轮 `urgent_sig` 相同则日志打 `[urgent-same]` 且**不重复告警** |

失败时只有 `last_attempt` / `ok:false` / `status:"failed"` / `reason`，reason ∈
`no_credentials` / `login_failed` / `no_courses` / `all_courses_failed`。
**`last_success` 在失败分支里保留上一次的值**（`_save_meta()` 先读旧 meta），
否则事后无法判断数据有多旧。README 的「数据源状态」和飞书告警都读它。

## data/diary/quotes.json

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `make_id(text)`——**按文本去重，不按文件**。同一句话在多天日记里重复出现只留一条 |
| `text` | str | 名言原文，AI 必须逐字引用，不许改写 |
| `context` | str | ≤60 字的上下文说明 |
| `comment` | str | **AI 点评**，≤120 字（提示词要求 40 字内）。走 `PERSONA` 人格：先损一句再给具体动作。空串表示模型没话说 |
| `source_file` | str | Gitee 仓库内相对路径 |
| `source_date` | str | 从文件名/路径提取的 `YYYY-MM-DD`，可能为 `""` |
| `first_seen` | str | 首次挖到的日期 |
| `value` | int \| 缺失 | **AI 价值分 0–10**，由 `prompts.quote_value_messages()` 打。README 只展示分最高的 `QUOTE_LIMIT=3` 条。**缺失按 0 分排最后**，不报错 |
| `value_why` | str | ≤40 字的打分理由，**存下来供追溯，README 与看板都不渲染它**（只渲染 `value`） |

`extra meta: repo`。

**存量名言靠 `backfill` 模式补，不要清文件重抽**：`merge_quotes` 的 `_carry` 只填 old 里为空的字段，
而存量条目是加这些字段之前抽的。`main.py backfill` → `diary_collector.backfill_comments(batch=8)`
补 `comment`，两个出口都连带调 `score_quotes(batch=10)` 补 `value` / `value_why`。
`diary` 采集时也会当场给新名言打分，所以不用等 backfill。
**清 `quotes.json` 重抽会连带重抽计划，人工 `state` 标记有丢失风险。**
实测（2026-11-13）：15 条里 8 条带点评，正好是本轮新增的 8 条。

## data/diary/writeback.json

```json
{"updated_at":"...","last_date":"2026-11-14",
 "last_path":"总仓库个人-Sync/.../日/2026-11-14.md",
 "written":12,"done":["<pid>","<pid>"]}
```

| 字段 | 说明 |
|---|---|
| `last_date` `last_path` | **上一次写回的那天**。复查时读它，不是读「昨天」——跨天/漏跑都能对齐 |
| `written` | 本次写进日记的计划条数 |
| `done` | 复查时读到已勾选的 pid，采集侧据此把计划 `state` 改成 `done` |

日记里的区块格式（**只有区块内是助手的，区块外一个字节都不碰**）：

```markdown
<!-- assistant:plans:start -->
## 🤖 助手待办 · 2026-11-14
- [ ] 背单词 <!-- pid:abc123 -->
- [x] 跑步 <!-- pid:def456 -->
<!-- assistant:plans:end -->
```

`pid` 就是 `plans.json` 的 `id`。复查靠 pid 对齐，**不靠文本匹配**（用户可能改字）。

## data/diary/plans.json

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `make_id(text, source_file)` |
| `text` | str | ≤120 字 |
| `due_date` | str\|null | 严格 `YYYY-MM-DD`，不合规直接置 null |
| `confidence` | float | 0–1。复选框恒为 `1.0`；AI：明确承诺 0.9 / 强意向 0.7 / 模糊 0.4 |
| `state` | str | `open` / `done` / `cancelled` |
| `tags` | str[] | ≤3 个，每个 ≤12 字 |
| `origin` | str | **`checkbox`（程序确定性解析）/ `ai`（模型推断）** |
| `source_file` `source_date` `first_seen` `last_seen` | str | 同上 |

`origin` 决定合并权限，见 [工作原理.md](工作原理.md)：

- `checkbox` 是权威。你在 Obsidian 里把 `[x]` 改回 `[ ]`，程序必须跟着改。
- `ai` 不能推翻人工。`state == "done"` 或 `"cancelled"` 后 AI 再挖到同一条也不会重开。
- **`cancelled` 是唯一的人工字段**：想永久屏蔽某条 AI 幻觉，手改 `state` 为 `cancelled`，合并层会跳过它。这是允许手改生成物的唯一例外。

## data/diary/state.json

```json
{"last_run":"...","repo":"jiuyuan233/obsidion-gitee","branch":"master",
 "root":"总仓库个人-Sync/个人信息/个人信息/Tasks","file_count":27,
 "files":{"总仓库个人-Sync/.../2026-11-10.md":
   {"sha":"<git blob sha>","size":1234,"processed_at":"..."}}}
```

`file_count` 是扫描到的 md 总数，`files` 只含**处理成功**的。两者不等说明有文件待重试。

增量判断靠 **git blob sha**，不是 mtime（API 不给可靠的 mtime）。
只有处理成功的文件才写回 state，失败的下次自动重试。

| `first_seen` `last_seen` | str | |

## data/schedule/*.json

三个文件共享 meta：`semester_start` `total_weeks` `current_week` `today`
`event_count` `course_count` `this_week_count` `date_range:[起,止]`。

**events.json** — 一条 = 某周某天某次课（WakeUp 的 `RRULE:FREQ=WEEKLY;COUNT=1` 展开后）：

`uid` `date`(YYYY-MM-DD) `weekday`(0=周一) `weekday_cn` `start`/`end`(HH:MM)
`slot_start`/`slot_end`(节次 int) `slots`(节次数) `course` `topic` `room` `teacher` `week`(教学周)

**courses.json** — 按 `(course, topic, room, teacher, weekday, start, end)` 聚合，
额外 `weeks: [1,3,5,...]`。这是渲染周课表的数据源。

**this_week.json** — events 里 `week == current_week` 的子集。

`semester_start` 不是配置项，是**算出来的**：对每条 event 反推
`date - weekday天 - (week-1)*7天`，取众数。实测 = `2026-09-07`。

## data/sources.json（●唯一常规手改文件）

```jsonc
{
  "notice": [ {"name","url","enabled","pages","weight"} ],   // pages=最多翻几页
  "keywords": {"gate":[...], "boost":[...], "block":[...]},  // block 一票否决
  "diary":  {"repo","branch","path","max_files_per_run","max_chars_per_file",
             "daily_dir","max_writeback","writeback_window"},
  "study":  {"passport","course_list","middle","work_list","fid","refer",
             "max_courses","fetch_detail","max_detail"}
}
```

学校换域名时改这里，不要改代码。`max_*` 是 token / 请求量闸门。

`diary.writeback_window` 是**往用户日记仓库提交的时间窗**，北京时间 `HH:MM-HH:MM`，
含头不含尾，支持跨零点（`23:00-02:00`）。代码默认 `00:00-05:00`，当前配置 `00:00-06:00`
—— 用户白天在 Obsidian 里编辑，写回必须避开。窗口外 `diary` 仍然采集与复查勾选，但**一次都不提交**。
格式写错会失败关闭（当天不写）并在日志打 ERROR，不会退化成随时写。

**改这个值不需要动 cron**：`do_tick()` 发现「现在在窗口内」且 `runtime.writeback_date != 今天`
就强制加跑 `diary`，所以窗口内每 20 分钟都有一次机会。
**唯一的硬下限是窗口宽度必须 ≥ cron 间隔**，否则可能整天错过（见 DEV_GUIDE 第 2 节）。

## docs/data/*.json（前端快照）

由 `render_readme.py` 从 `data/` 复制/裁剪而来，**前端只读这里**（GitHub Pages 只能伺服 `docs/`）。

- `tasks.json`：`{updated_at, stats, items, courses}`。
  **`items` 只含过滤后的可做任务**（`actionable()` 的 `kept`），不是全量；
  `courses` 是 `study/courses.json` 的 items，供前端按课程分组。
  全量任务只在 `data/study/tasks.json` 里。
- `schedule_geo.json`：课表 SVG 的几何参数，由 `week_svg.py` 导出，供前端实时时间线复用：
  `width` `height` `pad` `gutter` `col_w` `row_h` `body_top` `today_col` `date`
  `class_minutes`(=45) `slots`(11 个 HH:MM) `generated_at`。
  **前端 `nowLineY()` 必须和 Python `time_y()` 用同一套锚点算法**，改一边就要改另一边。
- `meta.json`：`{updated_at, week, stats, sources}`
  - `week`：形如 `第 10 周 / 共 20 周` 的**纯文本**（README 里那份带 `**` 加粗，写 JSON 时已剥掉，因为前端用 `textContent` 渲染）
  - `stats`：`pending` `overdue` `today` `week` `later` **`unknown`** `dropped` `courses` `suffix`
    （**没有 done 计数**，已完成只进 README 的折叠块；`dropped` = `{overdue, not_pending}`）
  - `sources`：目前只有 `{"study": <study/meta.json 原样>}`，前端用它判断数据是否新鲜
- `notices.json` / `plans.json` / `quotes.json`：透传，但 **plans/quotes 的 `source_file` 字段被删掉**
  —— 那是私有日记仓库里的文件路径，不该出现在公开网页上（审计 §2.2）。
  前端「记录于」那一列因此显示 `source_date`，不是文件名。quotes 含 `comment` 点评与 `value` 价值分，
  看板按 `value` 降序取前 10 条（README 取前 3 条，同一套排序口径）。

`stats` 分桶口径（`render_readme.render_tasks` 里的 `counts`，前端 `app.js` 的 `bucketOf` 必须一致）：

| 桶 | 判定 |
| --- | --- |
| `overdue` | deadline < now |
| `today` | deadline 落在当天 |
| `week` | now < deadline ≤ now + 7 天 |
| `later` | deadline > now + 7 天 |
| **`unknown`** | **deadline 解析不出来（null）** |

五个桶互斥。**⚠️ `unknown` 绝不能并进 `later`** —— 抓不到截止时间不等于「很久以后」，
混进去会让一条其实早已逾期的作业看起来还很宽裕（用户报过的真实 bug，审计 §1.1）。
README 里这类任务标 `⚠️截止未知`、顶部出 🔴 告警；网页单列一桶、标题写「可能早已逾期，点进去自己确认」。

**注意**：`items` 已经过滤掉逾期/非待完成（**「超一周」规则已废除，v1.3.0**），
所以前端 `overdue` 桶正常情况下恒为 0；`unknown` 桶**不一定为 0**，那是需要用户自己去确认的。
前端的分桶视图尚未改成 README 那样的「按课程分组 + 活跃度排序」，这是已知待办。

改字段时三处要同步：本文件、`render_readme.py`、`docs/js/app.js`。

## data/runtime.json（●tick 的调度状态，禁止手改）

`main.do_tick()` 每轮读写。**这是「一条 cron 跑出多种频率」的全部状态**，删掉等于全部重置。

```jsonc
{
  "last_tick": "2026-11-14T09:20:03+08:00",   // 最近一轮 tick 的时刻
  "last_ok":  {"study": "…", "diary": "…", "notice": "…"},  // 各采集器最近一次「成功」
  "last_try": {"study": "…", "diary": "…", "notice": "…"},  // 各采集器最近一次「尝试」
  "pushed":   {"morning": "2026-11-14", "noon": "2026-11-14", "night": "2026-11-13"},
  "writeback_date": "2026-11-14",             // 最近一次成功写回日记的日期
  "errors":   {"notice": "HTTPError @ notice_collector.py:88: …"},  // 各采集器最近一次异常摘要
  "last_results": {"study": true, "finalize": true}         // 上一轮每个子任务的结果
}
```

**为什么 `last_ok` 和 `last_try` 都要看**：只看 `last_ok` 的话，一个持续失败的采集器
每 20 分钟就会被重试一次 —— 学习通会触发风控，AI 会烧光额度。
两个都看 = **失败也按自己的间隔退避**。`due_collectors()` 里任一戳距今 < `间隔 - TICK_SLACK_MIN` 就跳过。

**`pushed` 按日期记账而不是按小时**：值是 `YYYY-MM-DD`，所以一天最多一条。
配合 `PUSH_CATCHUP_HOURS = {"morning": 5, "noon": 5, "night": 2}`，7 点那轮没跑成 12 点前还能补，
中午那轮没跑成 17 点前还能补，晚上只补到当天 24:00（`target` 取今天的整点，跨零点不补）。

**`errors` 只存 `exc_brief()` 的摘要**（已脱敏、≤300 字符），不存完整栈。
成功后对应的键会被 `pop` 掉，所以这里留着的都是「还没恢复」的问题。

**重置方式**：整个文件删掉。**不要手工塞时间戳** —— 把 `pushed` 改成今天会导致当天不再推送。

## data/diary/plans_archive.json（●归档，禁止手改）

`dedup.archive_plans()` 把**已完成/已取消且 30 天没再出现**的计划从 `plans.json` 挪到这里，
结构与 `plans.json` 完全一致（同一个 `save_list` 写出，带 `updated_at` / `repo`）。

**`open` 计划一条都不归档。** 那是用户自己的意图，宁可主表长也不能替他丢。
归档只是让主表不被几百条陈年 done 淹没，**不是删除** —— 要查历史随时能翻这个文件。
`DIARY_EXCLUDE` 黑名单同样作用于归档（`drop_excluded()` 会清它）。
